# 规则详解与判例

十条硬性规则的边界与示例。规则原文见 SKILL.md；本文件回答"具体场景下怎么判"。

## 规则 1：标题主权在用户

适用于主题树中的**每一个** topic.md（根文件、领域文件、子领域文件一视同仁）。

**禁止**（对 H1/H2 一律不允许）：
- 用 `edit`/`write` 触碰任何 H1/H2 行（含 `#`/`##` 前缀行本身）
- 新增、删除、移动、合并、重命名标题
- "顺手修正错别字/标点"——标题有问题也只能建议
- nest 下"顺手帮新建的领域 topic.md 填好标题"——领域文件的标题同样由用户填

**允许**：
- 阅读、分析、引用标题
- 在 H2 之下新增/修改正文与 H3 及以下子结构（属于"填充/优化"，受规则 3、4 约束）

判例：
- 用户："同意，你帮我改吧。" → 仍不代改。给出精确的改前/改后对照文案，请用户自己编辑；改好后向用户确认再继续。
- nest 下为新建领域 topic.md 生成骨架 → 模板占位结构保留，H1/H2 留空请用户填（与旧文件新建流程一致）。

## 规则 2：提建议的方式

- 建议必须带理由（与主题定位、结构覆盖、读者视角的关系）
- 一次集中在少数几点；给出可直接粘贴的候选文案
- 用户不接受 → 记录即可，不反复推销
- nest 下可建议结构级事项（领域拆/并、某文件夹缺 topic.md、某条内容上浮/下沉），格式同标题建议：观察 + 候选方案 + 理由；决定权与动手权都在用户

## 规则 3：落笔前的提问（填充与优化同适用）

问题必须具体、基于搜索结果，而不是"你想要什么内容？"这类空泛问题。五个维度：
- **范围边界**：这节覆盖什么、明确不覆盖什么
- **侧重点**：几个候选方向里哪个优先
- **素材**：用户已有的资料、既定决定、硬约束
- **密度**：要点条数与粒度（默认 3–6 条、每条一句话）
- **存量**（仅优化路径）：现有内容哪些是既定决定必须保留、哪些方向要删、哪些只是措辞或密度调整
- **作用域**（仅 nest 必问）：这个要点属于本领域，还是该上浮到根纲领 / 下沉到子领域？与其他领域是否重叠？

用户回答含糊 → 追问一次；仍含糊 → 给出你的默认理解请用户确认，然后继续，不要停滞。

## 规则 4：一节一回合

措辞升级版：**一个 H2、且属于同一个 topic.md 文件，每回合一个。**

- 一个"回合" = 从收到用户消息到下一次停下等用户
- 回合内只允许对**同一个 topic.md 文件中的一个** H2 落笔（填充与优化都算）；即使其余各节都是空的
- 处理完即停：报告改动 → 问下一节处理哪个 / 是否满意
- **跨文件 = 跨回合**：即使用户一次点名两个文件（如"根文件加一节，再填 01-opengl 的一节"），仍拆两轮分别处理
- 用户在同一回合点名同文件两节并各自给了细节 → 仍建议拆两轮；用户坚持才连填两节

判例：
- 用户："把根 Topic.md 和 01-opengl/topic.md 各填一节。" → 复述涉及文件清单与建议顺序，本回合只处理其一，完成确认后再处理另一个。
- nest 下"把整张主题地图的空节都填了" → 更不可批量：逐文件逐节推进，每回合一个文件的一个 H2。

## 规则 5：持续对齐

- 处理前复述理解；动笔前问细节；落笔前给草案确认
- 复述要短：骨架列表 + 一两句话方向，不整篇背诵
- 用户纠偏 → 立即修正理解并复述新理解
- nest 下复述增加一句"本文件在主题树中的位置及其父级边界"（如："01-opengl/topic.md 隶属根纲领『渲染』节，范围不得超出根文件对该领域的定位"）

## 规则 6：网络搜索

- 每一节动笔前至少一次 `web_search`；搜索词 = 该节标题 + 用户回答中的关键词
- 优化已有内容时，搜索重点是对照：现有要点是否过时、缺了主流方向、术语不准、或细到不属于纲领
- 中文主题用中文、英文各检索一次往往更全面
- 草案中区分来源：检索得来的事实 vs 用户口述的决定（草案后附一句来源说明即可）
- 搜索不到可靠信息 → 告诉用户，问是否按用户口述经验填，或换角度再搜；不得编造
- nest 下搜索词以该领域范围为界：不检索领域外内容；检索发现相邻领域信息 → 记录下来在归属问题中向用户提出，不直接写进本文件

## 规则 7：纲领性

**进 topic.md 的**：
- 方向性判断、边界声明、优先级、术语定义、模块间关系

**不进的**：
- 具体实现步骤、代码、命令
- 穷举式清单、表格数据
- 长段落论述（每条要点一句话为默认）

nest 下粒度分两档（都不进实现细节）：
- **根纲领**：领域级方向，一句话一个领域，判定"过细"的阈值更粗
- **领域纲领**：子方向级要点

判例：
- "本节聚焦 X，不涉及 Y" ✅
- "配置参数 A 默认为 3，B 支持 5 种取值…" ❌（实现细节，属实现文档）
- 优化时把已填的"配置参数 A 默认为 3…"精简成"关注 A 的默认策略与取舍" ✅
- 优化时未经确认整段删除用户既定内容 ❌（存量问题须先问，见规则 3"存量"维度）
- 根文件 H2"渲染"下出现"顶点着色器需统一 uniform 布局" ❌（领域内部细节，根纲领只放领域级方向；建议下沉到对应领域 topic.md）
- 领域文件 H2"纹理"下放"纹理管线为主线，先 mip 与过滤，压缩格式选型后置" ✅（子方向级要点）

## 规则 9：Context 只读（写入权归 grill）

Context.md（根 + 领域，惰性创建）与 decisions/ 属于 **grill 技能的写入域**。本技能对它们只有读取权。

**禁止**：
- 创建、修改、删除任何 Context.md 或 decisions/ 下的文件——即使用户口头说"你记一下"
- 把候选共识（新术语/新规则/极端情况/决策）直接写进任何文件
- 为"方便后续"预建空 Context.md 或空 decisions/ 目录

**允许**：
- 读取作用域链上的全部 Context.md 并作为提问与起草依据
- 在草案后附「候选共识」清单，建议用户运行 grill 沉淀
- 用户明确要求记录时 → 给出候选文案/要点清单，指路 `/grill`，由 grill 会话确认后落笔

判例：
- 起草时发明了新说法"软光栅对照线" → 附候选术语条目建议 grill；不自行写入 Context。
- 用户："这个决定挺重要的，你记到 Context 里。" → 不代写：给出候选条目（背景/决定/理由），指路 grill。
- 发现 Context 缺一个常用术语 → 通读复述时提出缺口，建议 grill；不代建、不代写。

## 规则 10：共识先查后用

- **先查**：动笔前读取本文件作用域链上的全部 Context.md（nest 沿"最近祖先"到根；single 即根）。不存在 → 记为「尚无 Context」，照常起草。
- **沿用**：起草必须沿用 Context 既有术语与既有规则；同一概念不得另造同义词。发现既有条目过时/不适用 → 向用户指出，不得静默绕开。
- **冲突上报**：用户口述、搜索结果或既有内容与 Context 冲突 → 停下，并列两侧说法，`ask` 用户裁决"哪个对"。裁决前不落笔；裁决改 Context → 指路 grill，改 Topic → 走对应节流程。

判例：
- Context 把 PBR 定义为"基于物理的渲染管线（含 IBL）"，用户本节却说"PBR 只指材质建模" → 停下指出，问哪个对；不静默按任一方写。
- 用户用了新词"渲染管线图"而 Context 已有术语"渲染管线" → 建议沿用既有术语；确要换词 → 裁决后走 grill 修改术语表。
- 搜索结果的主流用法与 Context 既有定义不一致 → Context 是本工作区的权威：默认沿用既有定义；确有更新必要 → 指路 grill。

## 规则 8：作用域归属（仅 nest 有实际约束力，single 下自动满足）

**规则原文**：落笔对象永远是"当前选定的那一个 topic.md 中的某一个 H2"。内容疑似属于父级或子级作用域、或与其他领域重叠时，先向用户提出归属建议，得到确认后才写。禁止跨文件搬运内容。

**边界**：
- 起草领域文件前必读父级骨架（仅标题与方向，不通读父级全文），把父级边界作为规则 3"范围边界"问题的输入之一
- 内容疑似上浮（属于父级划定范围）→ 给"建议上浮"的候选文案，用户决定
- 内容疑似下沉（属于某子领域）→ 给"建议下沉"的候选文案，用户决定
- 父子矛盾（子级声明与父级定位冲突）→ 停下指出，用户裁决改哪边；agent 无权自动让子级服从父级，也无权反之
- 跨领域重叠 → 指出重叠的两侧文件，用户裁决各自边界
- **禁止跨文件搬运**：即使用户要求"把根文件的渲染要点搬进 01-opengl"，也只是给出建议文案（改哪两个文件、各改成什么样），由用户自己动手

判例：
- **越界**：01-opengl/topic.md 草案出现"游戏引擎 ECS 架构方向"（根文件把它划给了"架构"领域）→ 不静默删除。指出"该要点超出 01-opengl 的划定范围"，给选项：a) 收敛措辞使其只服务 OpenGL 学习；b) 建议用户更新根 Topic.md 对应节（根文件更新走它自己的单节流程，不与本节合并处理）。
- **父子矛盾**：根文件声明"渲染领域只学 OpenGL"，01-opengl/topic.md 却有"Vulkan 对比"节 → 停下指出冲突，用户裁决改哪边。
- **跨文件请求**："把根文件的渲染节要点下沉到 01-opengl" → 不代为搬运；给出两侧文件的候选改动文案，用户自己改。
- **根文件过细**：nest 根文件 H2 下出现领域内部细节条目 → 优化路径中建议下沉；根纲领"过细"判定阈值比 single 更粗（只放领域级一句话要点）。
