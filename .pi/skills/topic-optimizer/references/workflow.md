# 完整工作流程与话术

## 阶段 -1：模式判定（每次会话开始，先于一切文件操作）

1. `read` 工作区**根目录**的 `config.json`（注意：是项目根目录，不是 topic.md 所在的任意目录）。
2. 取 `topic_mode` 字段值，归一化：`trim().toLowerCase()`。
3. 判定：`"nest"` → 嵌套模式；`"singal"` 或 `"single"` → 单文件模式（`"singal"` 是文档主拼写，`"single"` 为等价容忍拼写）；其他任何值（含字段缺失、类型错误）→ 非法，走回退策略。
4. **config.json 永远只读不写**——配置主权在用户；归一化只是内心判定，绝不改写用户的文件。

### 回退策略（config 缺失 / 非法时）

核心原则：**绝不静默猜测 nest；推断必须伴随告知，落笔前必须经用户确认路径。**

| 情况 | 处理 |
|---|---|
| config.json 不存在 | 结构推断：收集工作区所有 topic.md（大小写变体，排除隐藏目录）。仅根目录一个 → 按 single；根 + 子目录 ≥2 个 → 按 nest。通读复述时告知"未找到 config.json，已按结构推断为 X 模式"，并建议用户补建（给出可粘贴内容，如 `{"topic_mode": "singal"}`） |
| JSON 解析失败 | 报告原始内容与错误位置；按结构推断临时模式；`ask` 用户修复或口头指定模式 |
| topic_mode 字段缺失 | 同上（结构推断 + 告知 + 建议） |
| 值非法（如 `"nested"`、`"multi"`、数字） | 同上。**不要**把 `"nested"` 映射成 nest——非法值一律走推断，让用户显式修正 |

缺省倾向 single 的理由（可向用户解释）：1) 向后兼容，存量项目行为零变化；2) single 是 nest 的退化情形，误判 single 代价远小于误判 nest；3) 符合"宁可多问，不可自作主张"——推断只影响读与复述，落笔必经 `ask` 确认，推断错误不会造成不可逆写入。

## 阶段 0：定位文件

### single 分支

1. `glob` pattern `topic.md`（工作区根目录优先；没有再试 `**/topic.md`；也没有再试 `**/Topic.md` 等**大小写变体**——文件名大小写以实际工作区为准；仍没有则问用户路径）
2. `read` 通读全文

### nest 分支

1. 递归收集全部 topic.md 及大小写变体（排除 `.git/`、`.jj/`、`.pi/`、`.omp/`、`node_modules/` 等隐藏与依赖目录）
2. 构建**主题地图**：文件树 + 每个文件的 H1 与 H2 计数 + 父子关系（目录层级即作用域层级；无 topic.md 的顶层文件夹标注"未纳管"）
3. 依据用户请求定位本次目标文件（完整决策流程见 `references/examples.md`）：
   - 请求含明确文件/目录路径 → 取"最近的祖先（含自身目录）topic.md"
   - 无路径但提到领域名（匹配根文件 H2 或文件夹名）→ 对应领域 topic.md；找不到该领域文件夹 → 边界情况 E2
   - 请求是总体框架层面（整体规划/领域划分/优先级/加新方向）→ 根文件
   - 纯内容关键词、无位置线索 → 与主题地图各文件 H1/H2 匹配：唯一命中 → 该文件；多命中/零命中 → `ask` 弹"作用域选择"（候选文件路径 + 一句话范围 + 空节/已填概况）
4. 无论哪条分支，开始处理前复述："本次操作对象 = `<相对路径>`，其上级作用域 = `<父文件相对路径>`"（根文件则无上级）

### 文件不存在

- single：用 `ask` 问：新建 / 用户提供路径 / 暂不处理。新建 → 读 `skill://topic-optimizer/assets/topic-template.md` 生成骨架文件，**标题留空**，请用户自己填 H1/H2；填好后回到阶段 1。
- nest：区分"根文件缺失"与"某领域文件夹缺 topic.md"（后者属未纳管，见 examples.md 边界情况 E2）。新建根文件读 `assets/topic-template.md`；新建领域文件读 `assets/domain-topic-template.md`；标题一律留空由用户填。

## 阶段 1：通读与复述（每次会话开始时）

### single 分支

向用户输出：
- 模式判定结果（config 命中，或推断来源与推断依据）——一句话带过
- H1/H2 骨架列表（只列标题原文，不改写）
- 每个 H2 一句话现状：空（待填充）/ 已有纲领（可优化）/ 内容疑似过细（建议优化）
- 你对该文件主题方向的理解（1–2 句）
- 既有共识概况（作用域链上各 Context.md 的规则/术语/极端情况/决策要点；不存在则注明「尚无 Context」）

### nest 分支（两步复述）

**第一步：全局地图复述**（默认只展示两层，更深层级选中后再展开）：

```
主题地图（nest 模式）：
- Topic.md（根）：H1「学习计划」；5 个领域节，3 空 / 2 已填
  ├─ 01-opengl/topic.md：「OpenGL 渲染实操」；4 节，全空
  ├─ 02-graphics/topic.md：「图形学理论」；3 节，1 空 / 2 已填
  └─ misc/：无 topic.md（未纳管）
```

**第二步：文件级复述**（按阶段 0 定位的目标文件，格式与 single 同）：
- 该文件 H1/H2 骨架列表 + 每节一句话现状
- 你对该文件主题方向的理解（1–2 句）
- **本文件在主题树中的位置及其父级边界**（如："01-opengl/topic.md 隶属根纲领『渲染』节，范围不得超出根文件对该领域的定位"）
- 既有共识概况（本文件作用域链上各 Context.md 的要点；不存在则注明「尚无 Context」）

然后用 `ask` 问：理解是否准确？本轮处理哪个文件哪一节（填充空节，还是优化某节已有内容）？是否有想听的标题/结构建议？

### 共识读取（single/nest 同，阶段 0 定位后立即执行）

`read` 目标文件作用域链上的全部 Context.md（nest 与 topic.md 同一套"最近祖先"规则；single 即根 Context.md）。存在才读，不存在不建（规则 9）。读取粒度以"是否影响本节提问与起草"为准：规则/术语/极端情况/决策四类各捕关键条目，不整篇背诵。发现既有条目与本节相关但已过时/不适用 → 在复述时向用户指出（修正走 grill，不代改）。

## 阶段 2：标题建议（仅当发现问题时）

格式：
> 观察：`## 当前标题` …
> 建议：`## 候选文案`；理由：…

用 `ask` 给选项：采纳（用户自己改）/ 不采纳 / 换个方向。
无论结果如何，落笔的永远是用户；你只记录结论。

## 阶段 3：单节处理循环（核心循环）

```
选定文件 + H2 → 判定节状态：空 → 填充路径；已有内容 → 优化路径
两条路径共用：读 Context 链(规则 10) → web_search → ask 细节问题(2–4个，nest 含作用域) → 起草(沿用 Context 术语) → 3.0 作用域校验(nest) → ask 确认 → edit 落笔(topic 文件) → 停，问下一节
```

### 3.0 作用域校验（nest 必做，single 跳过）

起草后、请用户确认前，对照父级骨架检查：
- **越界**：要点超出父级划定范围 → 不静默删除；指出并给选项：a) 收敛措辞使其服务本领域定位；b) 建议用户更新父级文件对应节（走该文件自己的单节流程，不合并处理）
- **矛盾**：与父级声明直接冲突 → 停下，用户裁决改哪边
- **上浮/下沉**：内容疑似属于父级或子领域 → 给归属建议文案，用户确认后才写

校验结论随草案一并展示给用户。

### 3.1 搜索

- 至少一次 `web_search`；关键词 = 标题 + 用户上下文中的词
- nest 下搜索词以该领域范围为界；检索发现相邻领域信息 → 记录并在作用域问题中向用户提出，不直接写进本文件
- 记录：可靠事实、主流术语、有争议的点
- 优化路径额外记录：现有要点里哪些被搜索结果印证，哪些过时、缺失主流方向或过细

### 3.2 提问（`ask`，2–4 个问题）

- 范围："这节是否覆盖 X？还是 X 归入另一节更合适？"
- 侧重："搜索显示常见做法是 A / B，你更想强调哪个？"（给 recommended）
- 素材："这块你有没有已定的决定或约束？"
- 密度："3–5 条要点够吗，还是要更细 / 更粗？"
- 作用域（nest 必问）："这个要点属于本领域，还是该上浮到根纲领 / 下沉到子领域？"
- 共识（Context 有相关条目时必问）："Context 把 X 定义为 A，你这节要表达的是 A，还是我们要修正它？"（修正走 grill，不代改）
- 存量（优化路径必问）："现有 N 条里哪些是既定决定必须保留？哪些方向要删？还是只调措辞/密度？"

### 3.3 起草

- 只起草这一个 H2 之下的内容
- 术语与规则一律沿用作用域链上的 Context 既有条目（规则 10）；确需新说法 → 先按"冲突上报"问清再入稿
- 区分来源：检索事实 vs 用户决定（草案后附一句来源说明）
- 保持纲领性（见 rules.md 规则 7；nest 下根/领域两档粒度）
- 优化路径的草案是**修订对照**：逐条标明 保留（原文）/ 改写（原因）/ 新增（来源）/ 删除（原因）；用户的既定决定权重高于检索结果，删除必须给理由并经确认，不得静默丢弃
- 起草中沉淀出的候选共识（新术语、新惯例、边界情况、值得记录的决定）→ 不写进任何文件，草案后附「候选共识」清单，建议运行 grill 技能沉淀（规则 9）

### 3.4 确认与落笔

- `ask`：直接写入 / 修改后写入 / 重来（nest 下校验结论已随草案展示）
- `edit` 只动**选定 topic 文件**的该 H2 与下一个标题之间的行；标题行绝不进编辑范围；候选共识不落笔（写入权归 grill，规则 9）；绝不触碰 Context.md 与其他任何文件
- 起草时发现内容其实属于另一节、另一文件、或与已填节冲突 → 停下问用户，不静默处理

### 3.5 回合结束

- 报告：本节改动摘要（几条要点、来源构成；nest 下含作用域归属结论）
- `ask`：满意吗？下一节处理哪个文件哪一节？
- 会话继续 → 回到 3.1；用户收尾 → 确认整体状态

## 反模式清单

- 一口气把所有空节填满 → 违反规则 4
- 跳过提问直接写 → 违反规则 3
- 没搜索就写 → 违反规则 6
- 写成实现文档 → 违反规则 7
- "我帮你把标题也改了" → 违反规则 1
- 用户未回应就自行连续推进 → 违反规则 5
- 该节已有内容就当"已完成"跳过，只处理空节 → 填充与优化同为处理路径
- 未问存量、未给修订对照稿就重写用户已写内容 → 违反规则 3、5
- 一个回合动了两个 topic.md 文件 → 违反规则 4、8
- 把领域细节写进根文件（或把根级方向写进领域文件）未经归属确认 → 违反规则 7、8
- 父子冲突静默以一方覆盖另一方 → 违反规则 8、5
- 未读父级骨架就起草子文件内容 → 违反规则 8
- config 缺失时不告知就按推断模式落笔 → 违反规则 5 与阶段 -1 回退原则
- 把候选共识直接写进 Context.md 或代建 Context ❌（规则 9，写入权归 grill）
- 用户口述与 Context 冲突仍照常起草 ❌（规则 10）
- 未读作用域链上的 Context 就动笔 ❌（规则 10）
- 同一概念另造同义词、不对照既有术语表 ❌（规则 10）
