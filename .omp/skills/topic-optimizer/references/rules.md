# 规则详解与判例

七条硬性规则的边界与示例。规则原文见 SKILL.md；本文件回答"具体场景下怎么判"。

## 规则 1：标题主权在用户

**禁止**（对 H1/H2 一律不允许）：
- 用 `edit`/`write` 触碰任何 H1/H2 行（含 `#`/`##` 前缀行本身）
- 新增、删除、移动、合并、重命名标题
- "顺手修正错别字/标点"——标题有问题也只能建议

**允许**：
- 阅读、分析、引用标题
- 在 H2 之下新增/修改正文与 H3 及以下子结构（属于"填充"，受规则 3、4 约束）

判例：
- 用户："同意，你帮我改吧。" → 仍不代改。给出精确的改前/改后对照文案，请用户自己编辑；改好后向用户确认再继续。

## 规则 2：提建议的方式

- 建议必须带理由（与主题定位、结构覆盖、读者视角的关系）
- 一次集中在少数几点；给出可直接粘贴的候选文案
- 用户不接受 → 记录即可，不反复推销

## 规则 3：填充前的提问

问题必须具体、基于搜索结果，而不是"你想要什么内容？"这类空泛问题。四个维度：
- **范围边界**：这节覆盖什么、明确不覆盖什么
- **侧重点**：几个候选方向里哪个优先
- **素材**：用户已有的资料、既定决定、硬约束
- **密度**：要点条数与粒度（默认 3–6 条、每条一句话）

用户回答含糊 → 追问一次；仍含糊 → 给出你的默认理解请用户确认，然后继续，不要停滞。

## 规则 4：一节一回合

- 一个"回合" = 从收到用户消息到下一次停下等用户
- 回合内只允许对一个 H2 落笔；即使其余各节都是空的
- 填完即停：报告改动 → 问下一节处理哪个 / 是否满意
- 用户在同一回合点名两节并各自给了细节 → 仍建议拆两轮；用户坚持才连填两节

## 规则 5：持续对齐

- 处理前复述理解；动笔前问细节；落笔前给草案确认
- 复述要短：骨架列表 + 一两句话方向，不整篇背诵
- 用户纠偏 → 立即修正理解并复述新理解

## 规则 6：网络搜索

- 每一节动笔前至少一次 `web_search`；搜索词 = 该节标题 + 用户回答中的关键词
- 中文主题用中文、英文各检索一次往往更全面
- 草案中区分来源：检索得来的事实 vs 用户口述的决定（草案后附一句来源说明即可）
- 搜索不到可靠信息 → 告诉用户，问是否按用户口述经验填，或换角度再搜；不得编造

## 规则 7：纲领性

**进 topic.md 的**：
- 方向性判断、边界声明、优先级、术语定义、模块间关系

**不进的**：
- 具体实现步骤、代码、命令
- 穷举式清单、表格数据
- 长段落论述（每条要点一句话为默认）

判例：
- "本节聚焦 X，不涉及 Y" ✅
- "配置参数 A 默认为 3，B 支持 5 种取值…" ❌（实现细节，属实现文档）
