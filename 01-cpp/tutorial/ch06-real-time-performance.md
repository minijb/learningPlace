## 分节正文

### 6.1 帧预算：一场每帧都考的 16.6ms 考试

先做算术。显示器的刷新率决定了你每帧有多少时间，这个换算要长在脑子里：

| 刷新率 | 单帧预算 | 直觉 |
| --- | --- | --- |
| 60 fps | 16.67 ms | 主流基准线，全部逻辑 + 渲染提交都要在它之内完成 |
| 144 fps | 6.94 ms | 电竞屏时代的主流目标——预算直接腰斩再腰斩 |
| 240 fps | ≈ 4.17 ms | 预算薄得像一张纸，任何「偶发的一次分配」都能撕破它 |

**掉一帧的账要这么算**：60fps 下你平时 16ms、突然有一帧 64ms——那一帧不是「慢了 4 倍」，而是这一帧只干了原计划 1/4 的活，剩下的画面内容全部顺延，玩家看到的是一次肉眼可见的卡顿。
**掉一帧 = 单帧预算 4 倍超支**，而玩家对卡顿的记忆远比对流畅深刻。

一帧的预算还要**分摊**给所有子系统。两个量级示意（教学示意数字，非实测，真实比例取决于你的游戏）：

| 子系统 | MOBA/竞技（每帧） | 开放大世界（每帧） |
| --- | --- | --- |
| 输入采样与响应 | 0.3 ms | 0.3 ms |
| 游戏逻辑（AI/技能/规则） | 3 ms | 4 ms |
| 物理模拟 | 3 ms | 2.5 ms |
| 动画更新 | 1.5 ms | 2 ms |
| 渲染数据准备与提交 | 4 ms | 5 ms |
| 等 GPU / vsync | 3 ms | 2 ms |
| OS 与驱动干扰（留白） | 1.9 ms | 0.9 ms |

逐项说说这张表怎么读（量级示意，重点看「形状」而不是数字本身）：

- **输入采样与响应**：把手柄/键鼠状态读进世界，喂给技能判定。它必须排在最前——晚一帧采样，玩家的操作就晚一帧生效，这是「手感」的第一现场。超支症状：操作「粘滞」，按键与画面之间隔着一层棉花。
- **游戏逻辑（AI/技能/规则）**：MOBA 里它是绝对主角（大量单位判定）；大世界则把它摊薄到每个 AI 只占零点几毫秒。超支症状：BOSS 战一打起来，全城 NPC 一起变笨。
- **物理模拟**：碰撞检测、刚体积分、射线查询。弹幕满天飞的游戏里它最先爆。超支症状：两团怪挤在同一片区域时，全场穿透或卡顿。
- **动画更新**：骨骼采样、混合树、状态机过渡。超支症状：同屏角色一多，全员动作「慢半拍」。
- **渲染数据准备与提交**：剔除、排序、组装 draw call、写命令缓冲。CPU 侧最大的一块，也是优化收益最直观的一块。超支症状：CPU 帧时间随画面复杂度线性上涨，GPU 却在闲着——活全压在 CPU 的组织工作上。
- **等 GPU / vsync**：CPU 提交完命令后等 GPU 画完。这一段不是浪费——你用它并行做下一帧的准备（第 3 节渲染器「提交与 present 分离」的收益就在这里）。
- **OS 与驱动干扰（留白）**：驱动偷做的调度、后台进程的偷袭。这部分不属于你，所以预算表永远要留白——**把 16.6ms 全部用满的预算表本身就是事故预告**。

两个引申，都很要紧：

- **「够快了」不存在**。预算表不是「及格线 60 分」，而是每帧都重考的限时考——上一帧 15ms 不代表这一帧也 15ms，玩家新加了一个技能特效、后台杀毒扫了下盘，分摊立刻变样。
- **帧时间一致性 > 平均值**。偶尔一帧 100ms 比平均 18ms 更伤手感：平均只涨一点，但那次卡顿玩家看得清清楚楚。这就是 6.2 的帧计数器要看 p99 而不是平均的原因——**抖动藏在尾部**。

再把「偶尔一帧 100ms 比平均 18ms 更伤」的机制说透，三笔账各记一笔：

- **输入延迟突变**：正常帧里你的点击在 16ms 内被响应；那 100ms 里，玩家的闪避键要等 6 倍的时间才被读走——闪避慢了，死了，玩家把这叫「我按晚了」，其实是帧超支。手感伤害最大的正是这种责任错判：玩家替你的卡顿背了锅。
- **动画与相机跳变**：动画系统按帧时间推进，一帧 100ms 等于角色沿运动曲线「瞬移」了 100ms 的位移——插值被打乱、相机猛拽一下，晕动感就来了。
- **流畅感是一致性**：人对流畅的感知对象是**稳定性**而非速度——30fps 稳定比 60fps 抖动更「顺眼」，这是显示行业的公论。所以 6.2 的帧计数器看 p99 而不是平均；主机平台认证条款里写的也是帧率**波动范围**，不是平均值。

还有个绕不开的词：**vsync（垂直同步）**。开启后你的帧会被强制对齐到显示器节奏——预算超支一点点（比如 17ms），实际表现不是「慢 0.3ms」而是**直接掉到下一档 33ms**：一整帧的惩罚。这就是为什么 16.5ms 和 16.9ms 是两个世界。

最后把「预算内/超支」落到玩家的实际感知分层上：**预算内时玩家什么都不会注意到——性能工作的最高奖赏就是没人提起你**。
超支的体验按程度递进：轻微超支（16→20ms）感知不到；vsync 档位跳变（→33ms）是「顿了一下」；连续多帧超支是「卡住了」；秒级冻结是「游戏是不是崩了」。你优化的每一个毫秒，都是在把这些台阶往下压一层。

预算超支时先砍谁？这张优先级清单来自「单位毫秒的玩家体验收益」：

- **先砍观众看不见的**：粒子数量上限、视距、非焦点单位的更新频率（LOD 的性能本质就是预算再分配）；
- **再砍能动态回弹的**：动态分辨率缩放（分辨率 ↓ → GPU 填充率 ↓，画质劣化最平缓）、特效精度档位；
- **最后才碰手感**：输入采样频率、物理步长——这两项一动，玩家立刻能感觉到「不对劲」。

反过来说：**预算内省下来的毫秒，优先「存起来抗抖动」而不是立刻花掉**——留白是 6.1 分摊表里最值钱的一行。

预算不只是个人工具，还能进团队流程：把「60fps 下逻辑 ≤ 4ms、渲染提交 ≤ 5ms、每帧堆分配 = 0」写进里程碑验收与代码评审的对照项——性能从「上线前突击优化」变成「每次提交都过的门槛」。后面深入专题的 alloc budget 断言，就是这个思路在代码层的落点。

还有一个容易混的词组：**帧率 ≠ 模拟频率**。渲染帧率盯着显示器节奏走（预算考试的主角），而物理/逻辑的模拟步长可以是固定的（比如 60Hz tick，累计时间补齐）——两者解耦后，渲染掉帧不至于让物理走样。
这套「固定步长模拟 + 可变渲染」的游戏循环设计是第 4 节的正题，你只需要先记住：**预算讨论的默认语境是渲染帧；模拟频率是另一条独立的预算线**。

章末观念指针一句：帧预算这套算法，就是第 3 节渲染器「渲染提交与 present 分离」、第 4 节游戏循环「固定/可变步长」设计成那个形状的性能出处——到各自章节你会认出它。

### 6.2 测量方法论：采样剖析器、帧计数器与时间线三分工

「游戏卡了」是一句没有信息量的话。性能问题先分类，再选仪器——三类问题，三种仪器：

| 问题 | 仪器 | 产出 |
| --- | --- | --- |
| 「哪里最慢？」 | ①采样剖析器 | 热点函数排名、火焰图 |
| 「这一帧几毫秒？抖动多大？」 | ②帧计数器 | min / p50 / p99 帧时间 |
| 「线程们各自在干嘛、谁在等谁？」 | ③时间线 | 跨线程甘特图、锁等待可视化 |

**① 采样剖析器：热点在哪**。Visual Studio 自带，入口 **Alt+F2**（或菜单 调试 → 性能探查器）：

1. 勾选 **CPU Usage**，目标选当前启动项目或「更改目标」指向现成 EXE；
2. 跑一段**代表性场景** 10–30 秒，停止收集——采集「平均场景」只能得到平均结论（6.1 的抖动教训在这里同样成立）；
3. 读报告。

它的工作方式是**采样**：每隔零点几毫秒看一眼「CPU 正在执行哪个函数」，谁被打断的次数多谁就是热点——所以它对目标程序零侵入，代价是精度以采样间隔为界。

报告里的**火焰图（flame graph）**这么读（示意，真实报告是交互式矩形图）：

```text
全部 CPU  ████████████████████████████ 100%
├─ GameWorld::update      ██████████████ 52%   纵深 = 调用栈层数
│   ├─ ParticleSystem::update ███████ 38%      横宽 = 该函数(含子调用)的 CPU 占比
│   │   └─ Particle::integrate █████ 31%        平顶 = 自耗时大头（优化就打这里）
│   └─ Animation::evaluate ██ 9%
├─ Renderer::submit       █████ 18%
│   └─ Mesh::bind         ███ 14%               ← 第二大耗时点
└─ Physics::step          ███ 15%
```

三个特征记牢：**横宽** = CPU 占比；**纵深** = 调用栈（下面的函数被上面的调用）；**平顶**（宽而浅的矩形）= 自耗时大头——它自己（而不是它调的人）在烧 CPU。
找前三大耗时点 = 找三块最宽的平顶。VS 报告里切到 Flames 视图，配合「热路径」提示与线程过滤器即可。

剖析器自身也有两个坑，先打预防针：

- **CPU Usage 看不见「等待」**：采样器只记 CPU 在执行谁的指令——主线程等锁、等 IO、等 GPU 的时间在它眼里是「闲着」，热点图上什么都没有。等待类问题要用时间线（③）或 VS 的「等待分析」，别拿错仪器；
- **内联会让归因失真**：优化器把小函数内联进调用方后，采样到的「热点函数」是内联后的合集，函数名未必是源码里那个函数——拿不准就降到 `/O2 /Ob1` 对照，或查符号窗口的内联标记。
第 5 章的内存序纪律在这里兑现：**要不要把 seq_cst 降级成 acquire/release？先看火焰图里锁操作是不是平顶，是，才值得动。**

拿到一份真实火焰图后的五个动作，按顺序来：

1. **找平顶**：扫一遍最宽的三块平顶——它们就是前三大自耗时嫌疑（对照自测题 2 的读法）；
2. **下钻调用栈**：宽而不深的块，先看它调用了谁——热点常藏在栈底几层；
3. **切线程过滤器**：主线程的 52% 里，有多少其实是工作线程干的活被 join 等待算进来的？逐线程看一遍再下结论；
4. **对准帧窗口**：把采集窗口对准「卡的那一帧」（先用②的帧计数器把尖峰帧标出来）——平均窗口会稀释尖峰；
5. **形成假设再去改代码**：火焰图只告诉「哪里贵」，不告诉「为什么贵」——把「Particle::integrate 31%」翻译成「该查数据布局了」（6.5）或「该查贵运算了」（6.10），再动手。

**② 帧计数器：这帧几毫秒**。剖析器回答「哪里慢」，帧计数器回答「每帧多久、抖不抖」——一个 `steady_clock` + 一个统计循环，十五行代码，却是全章出镜率最高的仪器。完整可编译的最小实现：

```cpp
// ch06_frame_counter.cpp —— 最小帧计数器：min/p50/p99 vs 平均（完整可编译）
// 「一帧的工作」用真实浮点计算模拟（约 3ms），每 50 帧插入一次 3 倍负载
// 模拟偶发尖峰（如异步加载收尾/ GC 式清扫）——负载形状固定、可复现。
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <vector>

namespace {
using clock_ = std::chrono::steady_clock;
double one_frame_work(int multiplier) {          // 千万次浮点累加 × 倍率
    double acc = 0.0;
    const int n = 10'000'000 * multiplier;
    for (int i = 0; i < n; ++i) acc += 1.0 / (1.0 + (i & 7));
    return acc;
}
} // namespace

int main() {
    constexpr int kFrames = 300;
    std::vector<double> ms;
    ms.reserve(kFrames);
    for (int k = 0; k < kFrames; ++k) {
        int mult = (k % 50 == 49) ? 3 : 1;       // 每 50 帧一次尖峰
        auto t0 = clock_::now();
        double sink = one_frame_work(mult);      // 计时循环内不打印（打印毁帧）
        auto t1 = clock_::now();
        ms.push_back(std::chrono::duration<double, std::milli>(t1 - t0).count());
        if (sink == 42.0) std::printf("(impossible)\n");   // 防优化：结果被「消费」
    }
    std::vector<double> sorted = ms;
    std::sort(sorted.begin(), sorted.end());
    double mean = 0.0;
    for (double v : ms) mean += v;
    mean /= static_cast<double>(ms.size());
    std::printf("帧数 %d（含 %d 次尖峰）\n", kFrames, kFrames / 50);
    std::printf("min = %6.2f ms\np50 = %6.2f ms\np99 = %6.2f ms\n平均 = %6.2f ms\n",
                sorted.front(), sorted[ms.size() / 2],
                sorted[(ms.size() * 99) / 100], mean);
    std::printf("结论：平均 %.2f ms 看似达标，p99 %.2f ms 暴露了尾部抖动\n",
                mean, sorted[(ms.size() * 99) / 100]);
    return 0;
}
```

本机实测（Release `/O2`）：

```text
帧数 300（含 6 次尖峰）
min =   8.90 ms
p50 =   9.83 ms
p99 =  29.96 ms
平均 =  10.25 ms
结论：平均 10.25 ms 看似达标，p99 29.96 ms 暴露了尾部抖动
```

三个要点：`steady_clock` 是单调钟，不受系统时间调整影响，计时只用它；**测量循环内不打印**（打印本身毁帧，统计完再输出）；**看分位数不看平均**——6 次尖峰把 p99 顶到 30ms，平均却只涨了 0.4ms，这就是「平均被 p99 背叛」的现场。

进阶两招（工程版帧计数器的标配）：

- **直方图**：把帧时间按 1ms 桶计数，一列星号打出来——整帧分布尽收眼底，双峰形态（大多数帧 9ms、少数 30ms）比任何单一分位数都直观；
- **超预算告警**：每帧检查「帧时间 > 16.6ms 就记一次违例」，连续 N 次违例时把那一帧前后的剖析数据自动存档——卡顿的现场证据，比玩家描述准一百倍。

接进真实游戏循环的姿势：帧首取时间戳、帧末入表（循环内不做任何 IO），统计与输出放在独立低频线程或「每 N 帧一次」的节拍上——计时本体必须零分配、零打印，它自己得先守 6.8/6.9 的纪律，否则仪器成了污染源。

**③ 时间线：线程们在干嘛**。前两件仪器都在看 CPU 花在哪，时间线回答的是**跨线程问题**：

- 异步加载线程有没有抢主线程的核？
- 主线程在等哪把锁？等了多久？
- 帧与帧的边界在哪？掉的那一帧里谁在忙？

第 5 章的「主线程渲染 + 工作线程加载」放进时间线，加载高峰是否压垮帧预算一目了然。

具体怎么读这条时间线：主线程一行，每个渲染帧一条块，块与块的间隙就是帧间隙；工作线程一行，加载任务是长条。三种典型形态，各说明一件事——

- **形态一（健康）**：加载条与主线程条首尾错开、互不重叠，主线程每帧块的长短纹丝不动——异步加载在真正「异步」，ch05 的架构兑现了；
- **形态二（锁等待）**：主线程块中间出现一段细长的等待缺口，缺口两端都是主线程自己的活——它在等某把锁或某个 join。那个锁就是你要治理的对象：缩小临界区，或把结果交接改成 ch05 的 atomic 发布（release/acquire）；
- **形态三（资源争抢）**：主线程块整体变长、且与加载条时间上重叠——工作线程在抢主线程的核或分配器（6.7 第三笔税的现场）。解法：线程亲和性分开摆，或给加载线程限频让路。

时间线类仪器的行业标配是 **Tracy**（github.com/wolfpld/tracy，Stages 阶段 6 指定资源）：在代码里插两行宏，就能在服务端窗口看到按帧分栏的时间线。
Windows 自带的对应物是 VS 的**并行堆栈/线程时间线视图**（调试会话里「调试 → 窗口 → 并行堆栈」），零接入成本，粒度粗一些——应急够用，长期还是 Tracy。

顺带认识**观测者效应**：测量本身会改变被测系统——采样剖析器偷走零点几毫秒、Tracy 的探针有开销、插桩越密帧越慢。
工程结论：① 剖析数据用于**找热点方向**（相对大小），不用于报绝对帧时间（绝对值归帧计数器管）；② 探针常驻但节制——每个函数都 Zone 的项目，时间线自己就成了一笔开销。

```cpp
// Tracy 接入示意（片段）：完整接入归实践任务 1（FetchContent 路线）
FrameMark;                                  // 帧边界标记：时间线上按帧分栏
ZoneScoped;                                 // 函数作用域标记：当前函数在时间线上成块
```

两个宏各说一句：`FrameMark` 画的是**帧与帧的分界线**——Tracy 服务端里整条时间线按它切栏，栏宽就是帧时间，哪一栏「胖了」一眼可见；`ZoneScoped` 画的是**函数作用域块**——插在哪个函数，那个函数就在时间线上亮出一块自己的条，块的嵌套纵深就是调用栈。
配合 `ZoneText` 还能给块贴字符串（比如「本帧加载了哪个资源」）。它们在 Release 构建下只是几条低开销探针——这正是时间线仪器能**常驻开发期**的原因，与深入专题「分配计数器常驻」是同一个纪律。

三分工决策表（背下来）：

| 症状 | 先用 |
| --- | --- |
| 「感觉整体慢」 | 采样剖析器找热点 |
| 「大部分时候流畅，偶尔卡一下」 | 帧计数器看 p99，再回剖析器找那一帧发生了什么 |
| 「加了多线程反而更卡 / 说不清谁在等谁」 | 时间线 |

决策表用起来就一句话：**症状决定仪器，仪器决定动作**——「大部分时候流畅偶尔卡」不要先开剖析器（平均窗口会稀释那次卡顿），先帧计数器定位尖峰帧，再带着时间戳回剖析器/时间线看那一帧里发生了什么。
仪器选错，后面全是白功。实战中三件仪器经常接力：帧计数器发现尖峰 → 时间线定位尖峰帧里的线程交互 → 剖析器下钻那一帧的热点——顺序错了，每一步都在浪费另一台仪器的采样窗口。

### 6.3 微基准的陷阱与纪律（兑现 ch04 误区五挂账）

你迟早会想写个小程序比一比两种写法谁快——这个冲动是对的，但微基准的地雷比代码本身还多。四个陷阱，逐个拆。

**陷阱一：Debug 下测性能，数据全部作废**。回收第 4 章误区五的挂账。MSVC Debug 是三样东西叠加的产物：

- `/Od`（关优化）——你写的循环原样逐条执行；
- 迭代器调试层——vector 的 `operator[]` 带越界检查，DEBUG 下还有额外的代理对象；
- 运行时检查——初始化填充、容器额外簿记。

同一个循环 Debug/Release 可以差数倍到一个数量级——你测到的可能全是调试脚手架的成本。**纪律：基准一律 Release `/O2`，Debug 数据只配看正确性。**

**现场症状**：同事跑来说「我这循环怎么要 800ms」，你问他怎么编译的——Debug。切 `/O2` 重测：9ms。所有「C++ 太慢了」的惊呼里，一多半是 Debug 数据在报警。
另一个变体：在 IDE 里直接 F5（默认 Debug 配置）看帧率，然后得出「我的渲染器不行」的结论——先看配置，再看代码。

**陷阱二：被优化器吃掉**。优化器有权删除一切「没有可观察副作用」的计算——这不是 bug，是 C++ 抽象机规则赋予它的自由。你的被测代码如果结果没人用，循环可以被整体消除，测出一个漂亮的 0 ms：

```cpp
// ch06_do_not_optimize.cpp —— 陷阱二现场：结果不被消费，优化器把循环整个吃掉
#include <chrono>
#include <cstdio>

double sum_unconsumed(const int* a, int n) {     // 反例：累加结果无人使用
    double s = 0.0;
    for (int i = 0; i < n; ++i) s += a[i];
    return s;                                    // /O2 下调用方不取返回值 → 循环可整体消除
}

double sum_consumed(const int* a, int n) {       // 纠偏：结果被强制「逃逸」
    double s = 0.0;
    for (int i = 0; i < n; ++i) s += a[i];
    volatile double sink = s;                    // volatile 写入：编译器不得删除
    (void)sink;
    return s;
}

template <class F>
double bench(F&& f, const int* a, int n, int rounds) {
    auto t0 = std::chrono::steady_clock::now();
    for (int r = 0; r < rounds; ++r) f(a, n);
    auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1 - t0).count() / rounds;
}

int main() {
    const int n = 50'000'000;
    std::vector<int> data(static_cast<std::size_t>(n), 1);
    // 反例：返回值丢弃。编译器/链接器视角：sum_unconsumed(a,n) 无副作用 → 直接删
    double t0 = bench([&](const int* p, int k) { (void)sum_unconsumed(p, k); },
                      data.data(), n, 3);
    // 纠偏：结果被消费
    double t1 = bench([&](const int* p, int k) { (void)sum_consumed(p, k); },
                      data.data(), n, 3);
    std::printf("未消费结果：%.3f ms（循环被优化器吃掉，耗时≈0）\n", t0);
    std::printf("volatile sink：%.3f ms（真实带宽出现了）\n", t1);
    return 0;
}
```

本机实测（Release `/O2`）：

```text
未消费结果：0.000 ms（循环被优化器吃掉，耗时≈0）
volatile sink：26.890 ms（真实带宽出现了）
```

纠偏惯用法：把结果写入 `volatile` 变量或指针解引用（「逃逸」到编译器看不到的地方），再配合打印双保险。
Google Benchmark 的 `benchmark::DoNotOptimize` / `ClobberMemory` 是同类做法的工业级封装（内联汇编强制「这个值被用了/内存被改了」）——本章示例不依赖它，但工程里建议直接用它。

**现场症状**：两个「版本」的基准测出耗时一模一样（常常都是 0.0x ms）；或者给函数加了个无关参数，计时反而变快了——这些都是优化器在提醒你「你测的不是你写的代码」。
隐蔽变体：迭代次数是编译期常数，整个循环可能被直接求值——把迭代次数改成运行期从 `argv` 读入，立刻现形。

**陷阱三：缓存冷热与预测状态**。首轮遍历数据还在内存里（冷），稳态遍历全在缓存里（热）——第 4 节你会看到这个差距的正式名字。纪律：**先空跑几轮预热，再开始计时**；本章所有实验都带了预热轮。

**现场症状**：同一基准连跑五次，第一次比后四次慢一截——那是冷缓存的「开机税」；更隐蔽的：先测 A 再测 B，B 的数据恰好被 A 留在缓存里（或反之），谁先谁后结论翻转。正解：各自预热、交错测量、多轮取中位数。

**陷阱四：微基准冠军 ≠ 游戏内冠军**。微基准是真空环境：无缓存竞争、无分支历史污染、数据集恰好贴脸。微基准只回答「两个实现**相对**谁好」；游戏内的绝对结论，必须回到游戏里用剖析器验证。

**现场症状**：微基准里 SoA 快 3 倍，进游戏帧时间纹丝不动——因为游戏里这个系统的热点根本不在数据布局，而在它上游的一次大分配。微基准赢了战役，游戏里看不见战场。

四个陷阱共享同一个底层逻辑：**基准测的是「这套测量方法」而不是「你的代码」**——配置、优化器、缓存状态、环境，任何一环掺假，数字就替你说谎。所以微基准的第一技能不是写基准，是怀疑自己的基准。

想长期做基准，接 Google Benchmark（github.com/google/benchmark）——FetchContent 三行接入（回收 ch04 4.7）。一个最小用例感受它的形状：

```cpp
// 片段：Google Benchmark 最小用例（依赖 google/benchmark，不随本章编译验证）
#include <benchmark/benchmark.h>

static void BM_StrideSum(benchmark::State& state) {
    std::vector<int> v(state.range(0), 1);
    for (auto _ : state) {                       // 框架自动多轮计时
        long long s = 0;
        for (std::size_t i = 0; i < v.size(); i += 64) s += v[i];
        benchmark::DoNotOptimize(s);             // 防优化内置（6.3 陷阱二）
    }
}
BENCHMARK(BM_StrideSum)->Arg(100'000'000);       // 参数化规模
BENCHMARK_MAIN();
```

`BENCHMARK` 宏 + `DoNotOptimize` + 自动多轮统计——6.3 的五条纪律，框架替你执行了四条（第五条「游戏内复测」仍归你）。五条纪律，每条给一句理由：

1. **Release `/O2`，Debug 数据作废**——否则测的是调试脚手架（陷阱一）；
2. **固定负载、可复现（固定随机种子）**——两次测的不是同一份负载，结论就不是对比而是抽签；
3. **预热再计，多次取稳态**——冷缓存与预测冷启动的「开机税」不该进样本（陷阱三）；
4. **结果必须被消费（防优化）**——不被消费的计算等于不存在（陷阱二）；
5. **微基准只下相对结论，游戏内复测才算数**——真空环境的冠军到了赛场未必是冠军（陷阱四）。


### 6.4 缓存层级：容量、延迟与那行 64 字节

CPU 计算快、内存慢，中间垫了一个多级的缓存金字塔。先把量级表立起来（**数量级示意，具体数值以你自己的 CPU 为准**——查型号或用 6.2 的仪器实测）：

| 层级 | 容量（典型量级） | 延迟（典型量级） | 归属 |
| --- | --- | --- | --- |
| 寄存器 | 几十个 × 8/16/32 字节 | ≈ 0 周期 | 每核私有 |
| L1 缓存 | 几十 KB | ~4 周期 | 每核私有 |
| L2 缓存 | 几百 KB – 几 MB | ~12 周期 | 每核私有 |
| L3 缓存 | 几 MB – 几十 MB | ~40 周期 | 全核共享 |
| 内存（DRAM） | 几十 GB | 200+ 周期 | 全家共享 |

给个人类尺度的类比感受一下差距：假设 1 个 CPU 周期 = 1 秒——从寄存器取数是「伸手就拿」，L1 是「起身开冰箱（几秒）」，L3 是「下楼取个快递（半分钟到一分钟）」，**去内存取一次是「出门跑一趟超市」**。缓存未命中的代价，就是把你的工作暂停在原地，等一趟外出采买。

把这张类比做成换算表（3GHz CPU 上 1 真实纳秒 ≈ 人类 3 秒）：

| 层级 | 真实延迟 | 人类尺度 | 等价的日常动作 |
| --- | --- | --- | --- |
| 寄存器 | ≈0 | 0 | 伸手就拿 |
| L1 | ~4 周期 | 几秒 | 起身开冰箱 |
| L2 | ~12 周期 | 十几秒 | 走到书架翻一下 |
| L3 | ~40 周期 | 半分钟到一分钟 | 下楼取个快递 |
| DRAM | 200+ 周期 | 几分钟 | 出门跑一趟超市 |

记住这张表的用法：热循环里每一万次 DRAM 访问，就是人类尺度里好几个工作日的停顿——所以 6.5 讨论的一切布局问题，本质上都是在「搬家」，让数据搬到离 CPU 近一点的地方住。

**缓存行（cache line）：64 字节，缓存搬运的原子单位**。这是本章最重要的一个数。

缓存和内存之间搬数据，不是缺一个字节搬一个字节，而是**一次搬整条 64 字节的缓存行**——你只想要 4 个字节，快递照样送来 64 字节的整箱。

回收第 5 章 5.9 的 false sharing，现在你知道机制出处了：两个线程各写自己的变量，只要两个变量挤在同一条缓存行上，这条行就在两个核之间乒乓——**硬件根本不知道你的「变量」边界，它只认 64 字节的行**。
`alignas(64)` 之所以能治它，就是把两个变量强制分进两条行。

与之配套的是**预取器**（prefetcher）：硬件会观察你的访问模式，检测到「顺序前进」或「规律步长」就提前把后面的缓存行搬好——你什么都不用做，只需**把访问模式排得规律**。
两条指导一切的原则：**时间局部性**（刚用过的数据马上还会用——留它住缓存）、**空间局部性**（用这个字节，附近字节马上也要用——这正是预取器爱吃的形状）。

两个原则各配一个游戏数据结构的小例子。**时间局部性**：粒子死亡时要把它的发射器状态拿出来改——刚写过的发射器数据还在缓存里，此时处理它几乎是免费的；但若发射器数组存在内存的另一头、中间隔着一万个粒子的数据，「刚用过」的优势就没了——相关数据要住得近，这是「组织数据布局」的另一半含义。
**空间局部性**：`vector<int>` 里第 i 个元素用完，第 i+1 个大概率马上也要用——连续数组天生长成预取器爱吃的形状；而 `list<Node>` 每个节点散落在堆的各处，next 一跳就是一次潜在的跨行访问（ch03 说 list 迭代慢，一半就慢在这里）。

预取器有明确的「喜欢/讨厌」清单。**喜欢**：顺序前进（遍历 vector）、固定步长（每隔 4 个取一个，几轮之后它连步长都学会了）、任何跨多次访问稳定重复的模式。
**讨厌**：指针追逐（链表/树每次跳向不确定的地址，它赌不准你下一拳打哪）、随机访问（乱序索引、哈希冲突链）。这就是「布局要规律」的硬件依据：**你的访问模式越像「扫」，缓存就越像不要钱**。

实验时间。同一份 2 亿 int（约 800MB，刻意大于 L3）的数组，想象成粒子的 life 数组，三种步长求和——工作量不同但访问模式不同，看硬件怎么收费：

```cpp
// ch06_stride_sum.cpp —— 缓存行/预取实验：同一数组，三种步长求和（完整可编译）
// 报倍数关系，不报绝对毫秒（跨机器不可比）。数组 2 亿 int ≈ 800MB，刻意大于 L3。
#include <chrono>
#include <cstdio>
#include <vector>

template <int STRIDE>
double bench_sum(const std::vector<int>& v, int rounds) {
    double acc = 0.0;                             // 累加结果最后被消费，防优化
    auto t0 = std::chrono::steady_clock::now();
    for (int r = 0; r < rounds; ++r) {
        for (std::size_t i = 0; i < v.size(); i += STRIDE) acc += v[i];
    }
    auto t1 = std::chrono::steady_clock::now();
    volatile double sink = acc; (void)sink;       // 结果被「消费」
    return std::chrono::duration<double, std::milli>(t1 - t0).count() / rounds;
}

int main() {
    const std::size_t n = 200'000'000;            // 2 亿 int ≈ 800MB（>L3）
    std::printf("分配 %zu MB……\n", n * sizeof(int) / 1024 / 1024);
    std::vector<int> life(n, 1);                  // 想象成粒子 life 数组
    bench_sum<1>(life, 1);                        // 预热：首轮冷缓存不计
    const double touches = static_cast<double>(n);
    double s1 = bench_sum<1>(life, 3);
    double s8 = bench_sum<8>(life, 3);
    double s64 = bench_sum<64>(life, 3);
    std::printf("步长  1：%.1f ms（%.0f 亿次触达，%.2f ns/次——每个元素都被用上）\n",
                s1, touches / 1e8, s1 * 1e6 / touches);
    std::printf("步长  8：%.1f ms（%.2f 亿次触达，%.2f ns/次——一条缓存行只交付 1/8）\n",
                s8, touches / 8 / 1e8, s8 * 1e6 / (touches / 8));
    std::printf("步长 64：%.1f ms（%.2f 亿次触达，%.2f ns/次——为 4 字节搬整条 64B 行）\n",
                s64, touches / 64 / 1e8, s64 * 1e6 / (touches / 64));
    std::printf("工作量降到 1/64，总时间只降到 %.2f 倍：省不下的大头，是在为缓存行粒度买单\n",
                s64 / s1);
    return 0;
}
```

本机实测（Release `/O2`）：

```text
分配 762 MB……
步长  1：119.3 ms（2 亿次触达，0.60 ns/次——每个元素都被用上）
步长  8：51.7 ms（0.25 亿次触达，2.07 ns/次——一条缓存行只交付 1/8）
步长 64：21.5 ms（0.03 亿次触达，6.87 ns/次——为 4 字节搬整条 64B 行）
工作量降到 1/64，总时间只降到 0.18 倍：省不下的大头，是在为缓存行粒度买单
```

读数方式比数字本身重要：工作降到 1/64，时间却只降到约 1/5——**每次触达的单价从 0.60ns 涨到 6.87ns，涨了 11 倍**。
因为步长拉大后，每消费一个 int，硬件照样得为你搬来整条 64 字节行（64 个 int），其余 63 个全浪费在路上。这就是「缓存行是交付粒度」的直观形态，也是 6.5 AoS/SoA 差距的机制根源。

顺手用 6.3 的纪律给这个实验做三问自检：**为什么是 800MB**——刻意大于 L3，让每次未命中都付全价（数据集缩进 L3 的形态见 6.5 的 10 万粒子档）；**为什么先预热一轮**——首轮冷缓存的开机税不进样本（陷阱三）；**为什么只报倍数**——绝对毫秒跨机器不可比，方向才是可复现的结论（纪律五）。
三个设计决定，全部能在 6.3 找到依据——好实验是纪律的产物，不是运气的产物。

反过来说一句防走极端：**缓存行对齐不是免费午餐**。`alignas(64)` 滥用的代价是对象膨胀——一个 20 字节的小结构体被对齐后独占一条行，数组空间翻三倍，反而把更多有用数据挤出了缓存。
对齐是「隔离高频写」的药（false sharing 现场），不是「贴上就快」的符。

> **兜底声明（粗体）**：本节的量级数字是**设计直觉，不是优化免检牌**。层级容量、预取器行为都随具体 CPU 变化——任何布局决策动手前，先回到 6.2/6.3 的仪器。

两句备忘，防走极端：一是缓存之外还有 **TLB**（页表缓存）——巨型数据集扫描时即使数据在缓存，地址翻译也可能未命中，这是「超大数据集连 SoA 都救不满」的隐性原因之一，概念知道即可；二是硬件预取之外还有**软件预取**（`_mm_prefetch` 一类指令）——等不到预取器开窍时手动点名，但这是指令级微操，火焰图定罪且数据布局无解时才动。

### 6.5 AoS vs SoA：遍历模式决定布局

既然缓存行是 64 字节整条交付，那数据**怎么摆**就直接决定了缓存行的「含金量」。两种摆法：

- **AoS（Array of Structs，结构体数组）**：`Particle p[100000]`——一个粒子的全部字段挤在一起。面向对象的直觉写法。
- **SoA（Struct of Arrays，数组结构体）**：`positions[100000]; velocities[100000]; lives[100000];`——按字段分家。数据导向的写法。

同一套粒子更新算法（重力 + 半隐式欧拉积分 + 寿命衰减），两版完整对照程序——这是本章的关键示例，与实践任务 2 同源：

```cpp
// ch06_aos_soa.cpp —— AoS vs SoA：10 万粒子，同一更新算法，两种布局（完整可编译）
// 算法：v += g*dt（半隐式欧拉积分）；p += v*dt；life -= dt。color 字段更新时不碰。
// 计时口径：Release /O2；预热 5 轮后计 30 轮取 p50；报倍数，绝对值随机器而异。
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <random>
#include <vector>

constexpr float kDt = 1.0f / 60.0f;             // 规模在 main 里按 10 万/100 万两档扫描

struct Particle {                    // AoS：一个粒子一个对象（44 字节）
    float pos[3];
    float vel[3];
    float life;
    float color[4];                  // 冷数据：更新时不消费，却与热字段同住缓存行
};

static void update_aos(std::vector<Particle>& ps) {
    for (Particle& p : ps) {
        p.vel[1] -= 9.8f * kDt;      // 重力
        p.pos[0] += p.vel[0] * kDt;  // 积分
        p.pos[1] += p.vel[1] * kDt;
        p.pos[2] += p.vel[2] * kDt;
        p.life -= kDt;               // 寿命衰减
    }
}

struct ParticleSystem {              // SoA：按字段存放（每个数组都是紧凑热数据）
    std::vector<float> pos, vel, life;
    std::vector<float> color;        // 冷数据单独放，挨不着热路径
    explicit ParticleSystem(int n)
        : pos(n * 3), vel(n * 3), life(n), color(n * 4) {}
};

static void update_soa(ParticleSystem& s) {
    const int n = static_cast<int>(s.pos.size()) / 3;
    for (int i = 0; i < n; ++i) {
        s.vel[i * 3 + 1] -= 9.8f * kDt;
        s.pos[i * 3 + 0] += s.vel[i * 3 + 0] * kDt;
        s.pos[i * 3 + 1] += s.vel[i * 3 + 1] * kDt;
        s.pos[i * 3 + 2] += s.vel[i * 3 + 2] * kDt;
        s.life[i] -= kDt;
    }
}

static void seed_pos_vel(std::vector<float>& pos, std::vector<float>& vel,
                         std::mt19937& rng, int kParticles) {
    std::uniform_real_distribution<float> d(-1.0f, 1.0f);
    for (int i = 0; i < kParticles; ++i) {
        pos[i * 3 + 0] = d(rng); pos[i * 3 + 1] = d(rng); pos[i * 3 + 2] = d(rng);
        vel[i * 3 + 0] = d(rng); vel[i * 3 + 1] = d(rng); vel[i * 3 + 2] = d(rng);
    }
}

template <class F>
double bench(F&& f, int warmup, int rounds) {
    for (int i = 0; i < warmup; ++i) f();
    std::vector<double> ms;
    ms.reserve(static_cast<std::size_t>(rounds));
    for (int i = 0; i < rounds; ++i) {
        auto t0 = std::chrono::steady_clock::now();
        f();
        auto t1 = std::chrono::steady_clock::now();
        ms.push_back(std::chrono::duration<double, std::milli>(t1 - t0).count());
    }
    std::sort(ms.begin(), ms.end());
    return ms[ms.size() / 2];        // p50
}

int main() {
    const int scales[] = {100'000, 1'000'000};       // 10 万 ≈ 4.4MB 缩进 L3；100 万 ≈ 44MB 冲出 L3
    for (int kParticles : scales) {
        std::mt19937 rng(7);                         // 固定种子：两种布局拿到同一份初始数据
        std::vector<Particle> aos(kParticles);
        {
            std::vector<float> pos(kParticles * 3), vel(kParticles * 3);
            seed_pos_vel(pos, vel, rng, kParticles);
            for (int i = 0; i < kParticles; ++i) {
                for (int k = 0; k < 3; ++k) { aos[i].pos[k] = pos[i * 3 + k]; aos[i].vel[k] = vel[i * 3 + k]; }
                aos[i].life = 1.0f;
                for (int k = 0; k < 4; ++k) aos[i].color[k] = 0.5f;
            }
        }
        std::mt19937 rng2(7);                        // 同一份种子
        ParticleSystem soa(kParticles);
        seed_pos_vel(soa.pos, soa.vel, rng2, kParticles);
        std::fill(soa.life.begin(), soa.life.end(), 1.0f);
        std::fill(soa.color.begin(), soa.color.end(), 0.5f);

        int warmup = kParticles <= 100'000 ? 5 : 3;
        int rounds = kParticles <= 100'000 ? 30 : 20;
        double taos = bench([&] { update_aos(aos); }, warmup, rounds);
        double tsoa = bench([&] { update_soa(soa); }, warmup, rounds);
        std::printf("【%d 万粒子｜AoS 数据集 %zu MB】AoS p50=%.3f ms｜SoA p50=%.3f ms｜差距 %.2f 倍\n",
                    kParticles / 10'000,
                    kParticles * sizeof(Particle) / 1024 / 1024,
                    taos, tsoa, taos / tsoa);
    }
    std::printf("（每粒子：AoS 44 B 热字段 28 B｜SoA 热数组 28 B；本机实测，方向稳定、倍数随机器）\n");
    return 0;
}
```

本机实测（Release `/O2`）：

```text
【10 万粒子｜AoS 数据集 4 MB】AoS p50=0.129 ms｜SoA p50=0.121 ms｜差距 1.07 倍
【100 万粒子｜AoS 数据集 41 MB】AoS p50=3.572 ms｜SoA p50=1.654 ms｜差距 2.16 倍
（每粒子：AoS 44 B 热字段 28 B｜SoA 热数组 28 B；本机实测，方向稳定、倍数随机器）
```

**这组数字比「SoA 快」四个字值钱得多——它同时验证了两件事**：

- **机制**：热循环只消费 pos/vel/life（28 字节），AoS 里每个粒子却是 44 字节——color 这 16 字节冷数据跟着热字段**一起塞满缓存行**。缓存行的交付粒度（6.4）决定了你为一半用不上的数据付了带宽和行数。
- **缓存容量是布局红利的一部分**：10 万粒子才 4.4MB，整个数据集缩进 L3 里，AoS 的浪费被大缓存兜住了（1.07 倍，几乎白送）；100 万粒子 41MB 冲出 L3，每次缓存未命中都要去内存搬整行，浪费立刻显形（2.16 倍）。**数据集越大、越贴内存，SoA 越赚。**

**什么时候 SoA 赢**：同质海量对象、更新时只消费窄字段子集——粒子和子弹是原型。

第 4 节 ECS 的 System 每次只摸几个 Component，形状正是这个。
到时你会看到 System 的标准长相：`for (auto& [pos, vel] : view)`——每次只摸自己需要的两个 Component，其他 Component 的字节根本不进缓存行。
**「Component 是纯数据、System 只摸所需」不是美学洁癖，是把本节的机制制度化。**

决策时问的问题只有一个：**热点循环到底消费哪几个字段？**展开成对照表：

| 问题 | 答「是」→ SoA | 答「否」→ AoS |
| --- | --- | --- |
| 热点循环只碰少数几个字段？ | 窄子集被海量遍历，冷字段纯拖累 | 字段总是整组消费 |
| 同类对象数量巨大（几十万+）？ | 数据集冲出 L3，浪费显形 | 数据集缩在缓存里，浪费被兜住 |
| 对象要整体传递/序列化？ | 拆散后重组成本高 | 整对象移动是常态 |

拿这张表对着自己的项目过一遍，多数系统的答案五分钟内就能出来。三个游戏实例，练一遍判断：

- **粒子/子弹**（10 万级，更新只碰 pos/vel/life）：SoA——原型案例，本节实测 100 万粒时 2.16 倍；
- **变换层级**（场景节点几千个，position/rotation/scale 总是整组算 TRS 矩阵）：AoS——字段结伴使用，拆了反而让每次消费多三次间接；
- **碰撞对列表**（每帧动态生成、用完即扔的 `struct ContactPair { int a, b; float depth; }`）：无所谓——数量小、生命周期短，重点给它配 6.8 的 arena，而不是纠结布局。

**什么时候 AoS 无害甚至更好**：字段总是结伴使用（Transform 的位置/旋转/缩放永远整组消费）、对象数量小（缓存装得下）、需要把整个对象当单位传递/序列化。

折中还有**热点字段拆分**：把最热的两三个字段拆出小 SoA，其余留在 AoS。比如粒子系统的 life 同时被「物理更新」读写、被「渲染淡出」读——把它单独拆成一个紧凑数组，两条热点路径各自顺序扫自己的字段：

```cpp
// 片段：热点字段拆分——热字段独立成紧凑数组，冷字段留在 AoS
std::vector<float>    lives;      // 热字段：两条热点路径各自顺序扫它
std::vector<Particle> particles;  // 其余字段：整体消费时才整组读
```

公平起见，SoA 也有代价，决策前一并掂量：

- **单对象访问变贵**：原来一次缓存行拿到整只粒子，拆开后读「一只完整粒子」要跳多个数组——如果调用模式以「随机访问单只」为主，SoA 反而吃亏；
- **管理复杂度**：一个系统变成 N 个平行数组，增删要处处同步（多个数组共用一套下标）；
- **接口传染**：改布局必然改接口，调用方全动——这是它「传染性」的出处。

真要迁移，工程顺序三步：① 先给现状建基线（6.2 帧计数器 + 剖析器确认它真是热点）；② 只拆**最热的那一个系统**，别全工程开花——SoA 改造传染性很强，接口一变调用方全动；③ 迁移前后跑同一套单元测试（布局变了遍历语义可能变，尤其涉及 swap-and-pop 的下标）。

结论（粗体）：**布局跟着「热点循环问哪些字段」走——先写出来、测出来，再决定拆不拆。**

### 6.6 分支预测：有序与无序的分野

现代 CPU 是**投机执行**的机器：遇到 if 不等条件算完，先赌一个方向把后面的指令做起来（流水线不空转），赌对了白赚，赌错了把流水线里做了一半的东西全部冲刷重来——一次预测失败的代价是十几到几十个周期。
而且它赌的不只是方向，还赌**目标地址**（跳去哪）；预测命中时整条流水线满速投机执行，分支看起来毫无成本。
投机执行还有个安全阀：赌错不能产生不可逆副作用，硬件会憋着所有写操作等你「验货」——所以预测的学费只在计时里收，账不会算错。分支目标预测器会记住历史：同一边走到底的分支近乎全中；每步都随机翻转的分支只能瞎赌。

经典实验：1000 万个 0–255 的随机数，同一个 `if` 双路累加——数据无序 vs 排序后：

```cpp
// ch06_branch_pred.cpp —— 分支预测实验：同一 if，无序 vs 有序数据（完整可编译）
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <random>
#include <vector>

template <class Vec>
double bench(Vec& v, int rounds) {
    auto t0 = std::chrono::steady_clock::now();
    for (int r = 0; r < rounds; ++r) {
        long long big = 0, small = 0;             // 双路累加：两支都干活
        for (int x : v) {
            if (x >= 128) big += x;               // 数据决定走哪支 → 预测器赌方向
            else small += x * 2;
        }
        volatile long long sink = big + small; (void)sink;
    }
    auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1 - t0).count() / rounds;
}

int main() {
    const int n = 10'000'000;
    std::mt19937 rng(42);                         // 固定种子，可复现
    std::uniform_int_distribution<int> d(0, 255);
    std::vector<int> v(n);
    for (int& x : v) x = d(rng);                  // 均匀分布：分支各半，预测器赌不准
    bench(v, 1);                                  // 预热
    double t_unsorted = bench(v, 5);
    std::sort(v.begin(), v.end());                // 排序后：128 边界处只翻转一次
    double t_sorted = bench(v, 5);
    std::printf("无序数据：%.1f ms（每步都在翻转分支，预测失败≈流水线冲刷）\n", t_unsorted);
    std::printf("有序数据：%.1f ms（%.2f 倍：同一边走到底，预测近乎全中）\n", t_sorted, t_unsorted / t_sorted);
    return 0;
}
```

本机实测（Release `/O2`）：

```text
无序数据：37.0 ms（每步都在翻转分支，预测失败≈流水线冲刷）
有序数据：3.8 ms（9.80 倍：同一边走到底，预测近乎全中）
```

排序一次，稳态遍历快了近 10 倍——数据没变、代码没变，变的只是**分支的历史形状**。

注意账要算全：排序本身是 O(n log n)，不是免费午餐。这笔账摊得平的前提是**一次排序、多次遍历**——排序 5ms、之后每帧遍历省 30ms，两帧回本；如果是「每帧重排一次只为下一遍遍历快」，那大概率是负收益。
数据导向设计的老规矩：**为后续所有遍历付费的一次性整理，几乎总是值的**。
设计提示：简单的条件累加（如 `sum += x>128 ? x : 0`）常被编译器优化成无分支的 cmov，实验就测不出差距了——所以本例用「双路不同活」的写法。写你自己的版本时也一样：**先实测，再定稿**；测不出差距的分支不值得优化。

**什么时候在乎**，三个条件同时满足才值得动手：① 这段代码在热循环内（火焰图上是平顶）；② 分支结果由**数据**决定（编译期就定死的分支预测器百发百中，白送）；③ 分支两侧的工作量不小（一两个周期的差异乘不上几万次也只是零头）。
典型游戏场景：存活/死亡混杂的对象集合逐帧处理——先按存活状态 `std::partition`（或用 6.8 的池）把同类聚堆，让每个循环内的分支走势一致：

```cpp
// 片段：partition-then-iterate——把分支的「随机性」搬出热循环
auto dead = std::partition(ps.begin(), ps.end(),
                           [](const Particle& p) { return p.life > 0.0f; });
for (auto it = ps.begin(); it != dead; ++it) { /* 活粒子：分支全走同一边 */ }
// dead..end 是尸体区：单独低频处理，或整段回收
```

partition 还有一层缓存红利：活粒子聚到数组头部后，每帧实际扫描的区间更紧凑——无效数据不再夹杂在热路径上，与 6.5 的 SoA 是同一个思想在两个维度的应用（布局维度 vs 顺序维度）。

**分支消除手法**（概念级，逐条两句）：

- **查表**：分支本质是「按条件从两个值里选一个」——那就把候选值都先算好放进表里，用下标去取。回收 ch03 3.12 的编译期正弦表：把「算」变成「查」，顺带把分支也消了；
- **无分支惯用法**：`std::clamp/min/max` 在主流编译器下会生成条件传送（cmov）指令——两个候选都算出来由硬件「选」，不再有可预测的跳转；
- **位技巧**：`x & 7` 替代 `x % 8` 这类（6.10 详述）；更激进的掩码混合可读性代价大，非热点不用；
- **cmov 一句话**：编译器做这件事通常比你稳——手写 `?:` 有时反而不被转成 cmov，先看编译器输出（Godbolt）再手工干预。

兜底不变：**先测量，火焰图上分支真成了平顶再动手。**

### 6.7 堆分配的隐藏成本：逐帧 new 为何大忌

`new Bullet{}` 一行代码，运行时替你跑完一整套流程，拆开编号看：

1. **分配器找块**：在空闲块结构（链表/池）里找一块 ≥ 32 字节的空位——快慢取决于碎片程度，碎块越多找得越久；
2. **多线程锁**：Windows 默认堆多线程安全，所有线程在同一把分配器锁上排队（衔接 ch05 5.3 的锁概念）——这就是第三笔税的出处；
3. **可能的系统调用**：空闲块不够 → 向 OS 要新页（VirtualAlloc/mmap 之类），一次成千上万周期，还可能伴随缺页中断；
4. **构造**：跑 Bullet 的构造函数——这部分才是你写代码时想的那个「new」，通常也最便宜；
5. `delete` 反着来一遍：析构 → 归还分配器（进空闲结构等待复用，不一定真的还给 OS）。

前三步是「税」，第 4 步才是你看见的代码。税按**次数**收——这就是为什么堆分配按「微秒级 vs 纳秒级」的尺度贵。

顺带把「new」的三个形态分清（深入专题的计数器要全部重载，原因在此）：`new T`（单对象）、`new T[n]`（数组，配 `delete[]`——配错是未定义行为）、placement new（在给定地址上构造，不分配内存——池和 arena 的底层机制）。
日常写代码只遇前两个；读引擎代码撞见第三个，知道它是「只构造不分配」就够了。

三笔隐藏税，逐笔点名，每笔配一个游戏现场：

1. **固定开销**：单次不贵，但帧循环里按「次数」计费——每帧 100 次就是每秒 6000 次。现场：弹幕游戏开了「全屏特效」选项后帧率掉三成，剖析一看是每个特效生成时 new 了几个临时对象——固定开销乘上弹幕密度，就是这样乘出来的；
2. **碎片**：长跑进程反复分配释放不同大小，空闲内存被切成鸡零狗碎——RSS 缓慢上涨、缓存局部性变差。现场：测试组提单「游戏越玩越卡」——玩家开两小时后找块变慢、偶发尖刺变密，根源常是碎片。自测信号：任务管理器盯着 RSS 玩一小时，或代码里定期 `GetProcessMemoryInfo` 打点——「稳定负载下 RSS 只涨不跌」就是碎片化的指纹；
3. **分配器竞争**：工作线程和主线程同时 new，锁上排队——多线程「加速」被分配器偷偷吃回去。现场：异步加载一开，主线程帧时间反而抖了（时间线上主线程块凭空多出等待缺口，6.2 的形态二/三）。解法：给工作线程配独立分配器或 arena，或限频让路。

再叠一层 6.4 的缓存视角：堆内存散落各处，指针跳一次 = 一次潜在的缓存未命中——分配策略也在暗中决定你的缓存命中率。

「次数比字节数敏感」值得单独论证一遍：

- **字节数**决定你**占多少**内存——内存占用骂的是它；
- **次数**决定你**交多少次税**——帧率骂的是它。

关键事实：一次分配 1MB 与分配 1 字节都要走一遍完整的分配器路径，「找块」开销在同一量级；而帧循环里 100 次小分配就是 100 次完整征税。所以 6.8 的工具全部瞄准「把次数降到 0」，而不是「把字节数调小」。

实验：100 万次「new 小对象 + 用 + delete」 vs 池化复用：

```cpp
// ch06_new_vs_pool.cpp —— 逐次 new/delete vs 池化复用（完整可编译）
#include <chrono>
#include <cstdio>
#include <vector>

struct Bullet { float pos[3]; float vel[3]; float life; int owner; };  // 32B 小对象

double bench_new(int n) {            // 每发子弹都向堆要一次、还一次
    auto t0 = std::chrono::steady_clock::now();
    double acc = 0.0;
    for (int i = 0; i < n; ++i) {
        Bullet* b = new Bullet{};
        b->life = 1.0f;
        acc += b->life;
        delete b;
    }
    volatile double sink = acc; (void)sink;
    auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1 - t0).count();
}

double bench_pool(int n) {           // 池化：一次性拿够，循环内零堆操作
    std::vector<Bullet> pool(64);    // 预先备好 64 发复用位
    auto t0 = std::chrono::steady_clock::now();
    double acc = 0.0;
    for (int i = 0; i < n; ++i) {
        Bullet& b = pool[static_cast<std::size_t>(i % 64)];   // 取复用位
        b.life = 1.0f;
        acc += b.life;
    }
    volatile double sink = acc; (void)sink;
    auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1 - t0).count();
}

int main() {
    const int n = 1'000'000;
    bench_new(100'000);              // 预热
    double tn = bench_new(n);
    double tp = bench_pool(n);
    std::printf("逐次 new/delete：%3.1f ms（%d 次堆往返）\n", tn, n);
    std::printf("池化复用：    %3.1f ms（0 次堆往返）\n", tp);
    std::printf("差距：%.1f 倍（本机实测，量级随分配器/机器而异）\n", tn / tp);
    return 0;
}
```

本机实测（Release `/O2`）：

```text
逐次 new/delete：27.1 ms（1000000 次堆往返）
池化复用：    0.5 ms（0 次堆往返）
差距：55.5 倍（本机实测，量级随分配器/机器而异）
```

注意池化版省的不只是分配的几十纳秒：`pool[64]` 是连续内存，64 发子弹挤在几条缓存行上——**分配策略同时买了缓存友好**（6.4 的账又来了）。

排在所有池化之前的零号纪律是**能上栈就上栈**：`std::array` 替代小容量 `vector`、`char buf[64]` 替代临时 string（6.9/深入专题两处都这么干了）——栈分配是「移动栈指针」级别，与堆分配差着两三个数量级，且绝不碎片化。
判定问题一句话：**容量上限是编译期常数吗？**是，栈；不是，才轮到 6.8 的工具箱。

分配还有一笔经常被忽视的账：**同样次数，位置不同伤害不同**。100 次分配摊在 60 帧里，每帧 1–2 次，谁也注意不到；100 次挤在同一帧（比如某系统偶尔补配一波资源），那一帧直接顶穿预算——这就是「分配尖刺」，也是 6.2 帧计数器 p99 抓到的常客。
所以治理目标除了「总量降零」，还包括「不许出现分配尖刺」——后者正是按帧分段计数器能抓、全局总量计数器抓不到的。

还有一个工程级选项叫**分配器替换**：mimalloc/tcmalloc 这类多线程分配器把「分配器竞争」那笔税大幅削减（每线程缓存 + 无锁快路径），接入成本约等于链接一个库。
值得知道它的存在与定位——它是「让分配变快」，而本章纪律是「让分配变少」；前者是地板，后者是天花板，不互斥也不互替。

结论（粗体）：**帧循环里「分配次数」比「分配字节数」更敏感；热路径零分配是纪律，不是优化项。**


### 6.8 零分配工具箱：reserve、池、arena 与 swap-and-pop

五件工具，按改造成本从低到高，逐件过手。

**① reserve 预留**。回收 ch03 3.1/3.2：vector 扩容要「申请新块 → 搬家 → 析构旧块」，且让迭代器/指针全部失效。性能视角补上最后一刀：扩容搬家本身就是一次大分配，还是帧循环里反复出现的那种。知道上限就在帧初 `reserve` 一次：

```cpp
// 片段：局部示意
particles_this_frame.reserve(2048);   // 帧初一次；此后整帧 push_back 零分配
```

**② 对象池**。粒子和子弹的原型方案：先一次性备好一批，取用/回收都在池内循环，稳态零堆操作。完整小型实现（swap 栈版）：

```cpp
// ch06_pool.cpp —— Pool<T>：空闲下标栈 + 紧凑存储（完整可编译）
// 取「swap 栈」策略：回收位换到数组尾，O(1) 取/还；代价：元素下标会换位。
#include <cassert>
#include <cstdio>
#include <utility>
#include <vector>

template <class T>
class Pool {
public:
    void reserve(std::size_t n) { store_.reserve(n); }   // 预分配：杜绝中途扩容搬家
    template <class... Args>
    T& acquire(Args&&... args) {                 // 取一个对象（优先复用回收位）
        if (!free_.empty()) {
            int i = free_.back(); free_.pop_back();
            store_[i] = T(std::forward<Args>(args)...);
            return store_[i];
        }
        store_.push_back(T(std::forward<Args>(args)...));   // 池不够才增长
        return store_.back();
    }
    void release(T& obj) {                       // 还回池：swap-and-pop，O(1)
        int i = static_cast<int>(&obj - store_.data());
        assert(i >= 0 && i < static_cast<int>(store_.size()));
        std::swap(store_[i], store_.back());     // 尾部补位（自换位也无害）
        store_.pop_back();                       // pop_back 自带析构
        free_.push_back(static_cast<int>(store_.size()));   // 空位 = 原尾部下标
    }
    std::size_t size() const { return store_.size() - free_.size(); }
    std::size_t capacity() const { return store_.capacity(); }   // 预留容量：回收不缩池

private:
    std::vector<T> store_;
    std::vector<int> free_;
};

int main() {
    Pool<int> bullets;
    bullets.reserve(8);                  // 预分配：演示期间永不扩容搬家（引用保持有效）
    int& a = bullets.acquire(1);         // 发射 3 发
    int& b = bullets.acquire(2);
    [[maybe_unused]] int& c = bullets.acquire(3);   // 第 3 发（下方换位后引用失效，不再读）
    std::printf("发射 3 发：在池 %zu 发，池容量 %zu\n", bullets.size(), bullets.capacity());
    bullets.release(b);                  // 第 2 发命中回收：与尾部换位（c 的内容挪到 b 的位置）
    std::printf("回收 1 发：在池 %zu 发，池容量 %zu（容量不缩，回收位待命）\n",
                bullets.size(), bullets.capacity());
    int& d = bullets.acquire(4);         // 新一发：落在回收位上，零分配
    std::printf("再发射 1 发：在池 %zu 发，池容量 %zu（容量未增长——复用了回收位）\n",
                bullets.size(), bullets.capacity());
    std::printf("复用验证：a=%d d=%d（d 与 b 同槽）；c 的引用已随 swap-and-pop 失效，不再读\n",
                a, d);
    return 0;
}
```

本机实测：

```text
发射 3 发：在池 3 发，池容量 8
回收 1 发：在池 1 发，池容量 8（容量不缩，回收位待命）
再发射 1 发：在池 2 发，池容量 8（容量未增长——复用了回收位）
复用验证：a=1 d=4（d 与 b 同槽）；c 的引用已随 swap-and-pop 失效，不再读
```

这份 `Pool<T>` 为什么长成这样，拆开讲三点：

- **空闲位是「下标栈」而不是链表**：`free_` 存回收位的下标，acquire 弹栈、release 压栈——回收一个对象只做一次压栈，零搜索、零搬运；
- **存储始终紧凑**：活跃对象永远挤在 `store_` 前部，遍历全部存活子弹就是顺序扫数组——6.4 的空间局部性全额生效。链表版池每次 acquire/release 都在追指针，恰好踩中预取器最讨厌的「指针追逐」形状；
- **容量不缩**：`release` 后 `capacity()` 保持——池子只涨不缩，下一次高峰直接复用。这就是「预留制」纪律（回收 ch03 3.1 的 reserve）在池上的延伸。

**③ arena / 帧分配器（概念级）**：从一块大内存里「顶针」式顺序分配（bump allocator），帧末整体重置——分配退化为一次指针加法。引擎级标配，适合「当帧生、当帧死」的临时数据：

```cpp
// arena 帧分配器示意（片段）：帧初复位，帧内 bump，帧末整体重置
class FrameArena {
    char* buf_; std::size_t cap_, used_ = 0;
public:
    explicit FrameArena(std::size_t cap) : buf_(static_cast<char*>(::operator new(cap))), cap_(cap) {}
    ~FrameArena() { ::operator delete(buf_); }
    void* alloc(std::size_t n) {                       // 简化示意：无对齐/越界防护
        void* p = buf_ + used_; used_ += n; return p;  // bump：一次指针加法
    }
    void reset() { used_ = 0; }                        // 帧末：整帧分配一笔勾销
};
```

arena 的三个要点：**bump 分配**——「分配」退化为一次指针加法（`used_ += n`），没有任何查找，这是它能便宜过一切通用分配器的根本；**帧末整体重置**——`reset()` 只把指针拨回起点，一帧里分配的一千个临时对象一笔勾销，没有一个一个释放的仪式；**为什么不能 free 单个对象**——中间某个对象的内存还给谁？后面的对象全压在它上面，要释放它就得把后面全部搬家，bump 的「便宜」正是用「放弃单点释放」换来的。
所以 arena 只收「当帧生、当帧死」的租客（临时向量、每帧重建的命令数据），常驻对象别住这儿。与对象池的分工一句话：**池管「同一类型的高频生灭」，arena 管「当帧所有类型的临时量」**——粒子上池，粒子上方的伤害数字、临时 UI 字符串进 arena。

**④ swap-and-pop。回收 ch03 3.4 的 remove-erase 是「保序删除」的 O(n) 方案；如果容器**不需要保序**（粒子/子弹列表谁在前谁在后无所谓），O(1) 的做法是把要删的元素和尾部换位再 pop——上面 `Pool::release` 里就是这一手。
代价记牢：**换位后其他元素的下标/引用失效**，靠下标访问的并行系统要重新映射。
展开成一个小场景：你在做「技能锁定」系统，锁定了 17 号弹幕（存了它的下标 17）；同一帧里 3 号弹幕命中消失，swap-and-pop 把原本的尾部弹幕挪到 3 号位——如果 17 号恰是那颗被搬的尾弹，你的下标 17 现在指着完全无关的另一颗弹。
两个正解：改用深入专题 Pool 的「回收位标记」版（下标终身有效）；或锁定时记「身份」（世代号/generation），读回时校验——下标便宜但会撒谎，身份贵一点但诚实。

**⑤ 逐帧容器成员化**。函数内局部 `std::vector<...> tmp;` 每帧重建（分配+释放一对）；升格为类成员 + 每帧 `clear()`：**clear() 不缩容**（回收 ch03 3.1——容量留给下帧用），稳态零分配。深入专题的主角就是它。

五件工具先来一张对照表（细节见上文各条）：

| 工具 | 改造成本 | 消灭 6.7 的哪笔税 | 适用场景 |
| --- | --- | --- | --- |
| ① reserve/成员化 | 三行代码 | 固定开销（扩容类） | 帧内临时容器，几乎无条件先用 |
| ② 对象池 | 中（要管生命周期） | 固定开销（生灭类）+ 碎片 | 粒子/子弹等高频生灭 |
| ③ arena | 架构级 | 固定开销（临时类）+ 碎片 | 当帧生当帧死的大宗临时数据 |
| ④ swap-and-pop | 低（语义选择） | 间接消灭（容器紧凑） | 不需要保序的删除 |
| ⑤ string_view/延迟格式化 | 低 | 固定开销（拼串类） | 帧内一切字符串 |

使用顺序建议，按「改造成本 vs 收益」排成一条决策路径：

1. **第一档（零设计成本，永远先做）**：帧内临时容器 → 成员化 + `reserve` + `clear()`。改三行代码，消灭大部分「无脑分配」；
2. **第二档（中等成本，收益最大）**：改完还有高频生灭 → 上**对象池**（粒子/子弹/伤害数字）。选型看系统是否靠下标互指：是 → 回收位标记版（深入专题形态）；否 → swap-and-pop 版（遍历更紧凑）；
3. **第三档（引擎级决策）**：确定有「当帧生当帧死」的大宗临时数据 → 上 **arena**。它是架构决定（谁持有缓冲、帧末谁 reset），开局就该定，中途插入改造代价大；
4. **全程顺手**：字符串治理（6.9）不是独立优化项，遇到就做；swap-and-pop 是容器语义的选择，跟着数据形状走。

顺带回答一个实操问题：**reserve 的上限怎么定**？三步——先取一个「峰值 × 1.5」的经验值跑起来；再用分配计数器观察「reserve 之后还有没有容器分配」（有 → 上限不够或漏了某条路径）；最后在 Debug 断言里钉死「稳态帧容器分配为 0」。
上限本身不神圣，**「reserve 之后不再分配」才是可断言的硬指标**。

池的三个常见坑，先打预防针：

1. **忘记归还**：粒子死亡却没 `release`——池只涨不缩，泄漏从「内存泄漏」变成「容量泄漏」，计数器上表现为在池数持续上涨（所以深入专题的输出里带 `alive` 计数）；
2. **重复归还**：同一对象 release 两次——free 栈里出现两个同下标，下一次 acquire 两个系统拿到同一个位。防法：release 前断言「该位不在 free 栈」（Debug 开销换正确性）；
3. **构造/析构语义**：回收 ≠ 析构——swap 栈版 `pop_back` 会析构，回收位标记版不析构（元素原地保留）。选哪种要与「对象状态是否需要重置」一起决定，别混着用。

### 6.9 字符串：string_view 传参与临时字符串规避

回收 ch03 3.3 的两个事实：

- `std::string_view` **借而不拥有**——不拷贝、不分配，只是「一段内存的地址 + 长度」；字面量可用 `using namespace std::literals;` 后的 `"xxx"sv` 直接构造，连 string 临时体都不用建；
- **SSO**（短字符串优化）让约 15 字节内的短串直接住在 string 对象里，免上堆。

性能视角补一刀：这两条纪律在帧循环里不是洁癖，是**保命**——帧内拼接字符串是分配计数器上的头号惯犯。

#### 帧内拼串的三宗罪（对齐 6.7 的税单）

1. **分配**：`"frame " + std::to_string(frame)` 从第一次拼接起就冲出 SSO 边界，堆上分配；
   - 每一帧稳定触发一次——深入专题 STEP=0 里那顽固的「每帧 1 次」就是它；
   - 它贵不在单次，在**从不缺席**：60fps 一秒 60 次，一小时 21.6 万次；
2. **拷贝**：拼接是逐字符 memcpy，串越长拷得越多；
   - 帧预算里最冤的一笔开销——干的活对游戏毫无价值；
3. **释放**：临时 string 析构再归还一次；
   - 一来一回，一次日志 = 两次完整的分配器征税（§6.7 编号步骤 1–3 + 5）。

而这整串字符的唯一用途，是被打印或者被丢弃。

#### 怎么发现自己在犯案

- **仪器**：分配计数器（深入专题）突然多出几笔——八成是新加的日志或拼 key；
- **纪律**：code review 时，帧循环里出现 `std::string` 局部变量或 `+` 拼接，直接问一句「这串每帧都要存在吗」。

#### 四个治理方案

**① 传参用 `string_view` / `const char*`**：接口约定改成借用，调用方拿字面量、string、切片来都不产生分配（回收 ch02 的「借用」词汇表）：

```cpp
// 片段：借用式接口——三种实参，零拷贝零分配
void log_msg(std::string_view msg);
log_msg("player_died");                     // 字面量：不分配
log_msg(std::string_view(s).substr(0, 8));  // 切片：不分配
```

**② 日志分级，延迟格式化**：

- 常规帧连「一切正常」这四个字都不该存在——日志等级不够就 `if` 掉，格式化根本不发生；
- 深入专题 STEP=3 的「每 100 帧才格式化一次」是它的收敛版；
- 错误真发生了才 format——那时多贵都值得，因为它是小概率事件；
- 等级参考：**Error**（立即格式化，永远输出）/ **Warn**（输出但节流：同一条一秒至多一次）/ **Info**（进环形缓冲，出事才倒出最近 N 条）/ **Trace**（Release 下编译期剔除，连判断都不存在）。分级 log 系统是引擎标配，原理就是这四条。

**③ 高频 key 静态化/缓存**：

- 资源查表的 key 每帧现拼（`"tex_" + name`）是另一种惯犯；
- 高频 key 提成 `static const std::string`，或直接 `string_view` 指向字面量；
- 运行期才确定的 key 做「名字 → 句柄」缓存：同一字符串只拼一次，之后全部走查表——

```cpp
// 片段：key 缓存——拼串只发生在首次 miss
std::unordered_map<std::string, TexHandle> cache;
TexHandle get(const std::string& dir, const std::string& name) {
    static thread_local std::string key;        // 复用容量（6.8 ⑤ 的 string 版）
    key.clear(); key.reserve(dir.size() + name.size() + 1);
    key += dir; key += '/'; key += name;
    auto it = cache.find(key);                  // 查表：零分配
    if (it != cache.end()) return it->second;
    return cache[key] = load_tex(key);          // miss 才分配一次
}
```

**④ 格式化用 `std::format`（C++20），零分配场景退回 `snprintf`**：

- `std::format` 类型安全、语义清晰，本教程主环境 MSVC 下完整可用；GCC 13+/libc++ 17+ 才有，跨平台工程以工具链为准；
- 但注意：`std::format` 返回**新的 string**——它治理的是「写起来安全」，不是「零分配」；
- 热路径要零分配格式化：`snprintf` 写进栈缓冲（深入专题 STEP=3 演示的就是这一手）。

补一个「确实绕不开要拼」的场面：资源路径 = 目录 + 名字，加载期总要拼。惯用法是**先 reserve 再 append**——一次分配，而不是 += 五次扩容五次：

```cpp
// 片段：不得不拼时——先 reserve 再 append，一次分配
std::string path;
path.reserve(dir.size() + name.size() + 1);
path += dir; path += '/'; path += name;
```

注意这个模式的边界：它把五次分配变一次，仍是**一次**分配——加载期可以接受，帧循环里依然违规。纪律的适用性分级：帧循环零容忍、加载期一次可容忍、启动期随意。

最后一个必须钉死的坑：**string_view 借而不拥有 = 会悬垂**。借来的视图不延长被借者的命——最经典事故是「函数返回临时 string 的 string_view」，返回瞬间临时析构，视图指向自由岗。
纪律（回收 ch02 的生存期词汇表）：string_view 只做**参数**（调用期内使用），不做**成员或返回值**；确实要存，存 `std::string`。ch03 3.3 讲过悬垂三态，这里是它性能侧的回马枪。

一句话纪律（粗体）：**热路径上的字符串要么借用（string_view），要么根本不存在（延迟格式化）。**
### 6.10 贵运算清单：除法、开方与「先测量」

最后一份「嫌疑人清单」——每一项都真实存在贵运算，但每一项都要先测量再定罪（量级数字的权威出处是 Agner Fog 优化手册，见延伸资源）。先立一张量级对照表（数量级示意）：

| 运算 | 典型周期量级 | 相对加/乘 |
| --- | --- | --- |
| 加 / 乘（整型、浮点） | 1 – 5 | 基准 |
| 整型除法 / 取模（运行期除数） | 20 – 40 | 贵一个数量级 |
| sqrt | 15 – 30 | 贵数倍 |
| sin / cos / atan | 几十 – 上百 | 贵一个量级 |
| 编译期常数除法 | 被改写成乘法+移位 | ≈ 免税 |

#### 嫌疑人一：整型除法 / 取模

- 真贵的只有**运行期除数**——除数来自配置文件或玩家输入的除法，才是火焰图上会发光的那种；
- 两个重要豁免：
  - **除数是编译期常数**：编译器自动把除法改写成「乘法 + 移位」（魔法数技巧），所以 `x / 8`、`x / 1024` 根本不贵——别自作聪明改成移位牺牲可读性；
  - **模 2 的幂**：直接写位掩码 `x & 7`、`x & (n - 1)`，语义等价且便宜——注意位掩码只在除数是 2 的幂时等价，任意常数别乱套；
  - 改写是否真的发生了，一眼可验：Godbolt 上看汇编（`imul`/`shift` 出现即改写成功，`idiv` 出现即没改）——「信任但验证」编译器。

#### 嫌疑人二：sqrt 与 rsqrt

- 游戏现场：逐粒子归一化 `v / length(v)` 是热循环常客——`length` 一次 sqrt，向量除法再叠一份（回到嫌疑人一），一次归一化交两笔税；
- 图形学经典解法：快速倒数平方根 = 一次 rsqrt 近似指令（精度粗糙但只要几个周期）+ 一次牛顿迭代拉回精度——Quake III 那段 `0x5f3759df` 传奇代码就是它；
- 改造后的账：归一化从「sqrt + 除法」变成「一次 rsqrt + 几次乘法」；
- 两个提醒：数学推导归第 2 节，这里记住量级与名字；现代 CPU 已内置 `rsqrtss` 一类近似指令，别急着抄魔法数。

#### 嫌疑人三：超越函数（sin / cos / atan）

- 比四则运算贵一个量级（几十到上百周期）；
- 游戏现场三个常见惯犯：
  - 每帧给每粒子算 `sin(age)` 做闪烁——用 `constexpr` 编译期正弦表查表替代（回收 ch03 3.12：把「算」变成「查」，顺带把分支也消了）；
  - 角度归一化用 `fmod`——量化成整数后用掩码更便宜；
  - 缓动函数每帧重复求值——预先烘焙成查找表。

#### 嫌疑人四：浮点 ↔ 整型转换

- x87 时代每次转换要改 FPU 状态字（几十周期还串行化流水线），是老一辈优化手册里的大项；
- 现代 SSE/AVX 已改善到个位数周期——量级意识保留，定罪权归火焰图；
- 顺带一句：`float`/`double` 隐式混用主要是正确性问题（ch01 讲过收窄），性能上现代硬件几乎免费。

#### 收尾铁律（粗体）

**这份清单是「嫌疑人名单」，不是「见着就改清单」——火焰图定罪，再动手。**

为什么态度要这么拧巴？这族优化有两个共同的坑：

1. **微基准里总是有效**——单测一个除法当然测得出倍差，但放进真实帧循环常被缓存/分支的更大账单淹没：「微基准冠军 ≠ 游戏内冠军」（6.3 陷阱四）在这族优化上出现频率最高；
2. **手工替换常牺牲可读性**——而编译器对常数形态的处理多半比手写更优（Godbolt 验证后再动手）。

拿本章的表格走一遍「定罪流程」作结（四栏示范，与任务 1 的产出同构）：

- **问题**：火焰图上 `Particle::integrate` 占 31%，是最大平顶；
- **假设**：每粒子归一化含 `sqrt` + 向量除法，两次贵运算（6.10 嫌疑人一/二）；
- **改动**：归一化改 rsqrt 近似 + 乘法；数据布局同时换 SoA（6.5）——一次只改一个变量才可归因，所以分两轮做；
- **数据**：第一轮 rsqrt 替换 p50 降 8%；第二轮 SoA 再降 12%——两笔各归各的账。

GPU 侧有同名的方法论（基线 → 剖析 → 改动 → 复测），那是第 5 节性能工程的家当，观念先通上电。
## 深入专题：一次零分配改造的完整解剖

ch02 深入专题用「分配计数显微镜」回答过一次性的问题：make_shared 到底分配了几次。
本章给同一台仪器装上**时间轴**（按帧分段打印「第 k 帧：分配几次」）和**断言纪律**（帧分配预算），把它从一次性实验仪器升级为**开发期常驻护栏**——这是引擎团队的真实做法。

主角是一个「模拟帧循环」程序：2000 粒子更新，外加帧循环里最常见的**三宗罪**——① 帧内临时 vector 无预留地 push_back；② 每帧用 `std::string` 拼日志；③ 每帧 `new` 8 个特效子弹。
程序用宏 `STEP`（0→3）控制改造进度，每个阶段一版构建。先看完整源码（起点形态 STEP=0）：

```cpp
// ch06_zero_alloc.cpp —— 零分配改造解剖：分配计数器 + 四阶段改造（完整可编译）
// 阶段由宏 STEP 选择：0=起点（三宗罪）/ 1=容器成员化+reserve / 2=+Bullet 池化 / 3=+字符串治理
// 构建：cl /nologo /utf-8 /std:c++20 /EHsc /W4 /O2 /DSTEP=0 zero_alloc.cpp
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <string>
#include <vector>

// ============ 分配计数显微镜（ch02 深入专题升级版：四形态 + 按帧分段） ============
namespace alloc_probe {
std::size_t g_count = 0;             // 单线程主循环：普通 size_t 够用；
                                     // 多线程需 atomic（见 6.7 分配器竞争）
std::size_t g_frame_base = 0;        // 帧首基线
} // namespace alloc_probe

static void* probe_alloc(std::size_t n) {
    void* p = std::malloc(n);
    if (p) ++alloc_probe::g_count;   // 计数器内绝不 printf/抛异常：printf 自身可能分配 → 递归
    return p;
}
void* operator new(std::size_t n) { return probe_alloc(n); }
void* operator new[](std::size_t n) { return probe_alloc(n); }
void operator delete(void* p) noexcept { std::free(p); }
void operator delete[](void* p) noexcept { std::free(p); }
// 注：C++17 对齐重载（align_val_t）在本演示中不会触发（对象对齐都不超过默认对齐）；
// 真实工程需把对齐形态一并重载，防止漏计。

// ============ Pool<T>（简化收录：空闲下标栈版，6.8 有 swap-and-pop 版对照） ============
// 回收只标记「洞」，不搬元素：下标终身有效——本场景按句柄回收天然安全。
// （6.8 的 swap-and-pop 版会搬尾补洞、遍历更紧凑，代价是下标换位，见正文警示。）
template <class T>
class Pool {
public:
    void reserve(std::size_t n) { store_.reserve(n); }   // 预分配：杜绝扩容搬家
    int  acquire() {                                     // 取下标：优先复用回收位
        if (!free_.empty()) {
            int i = free_.back(); free_.pop_back();
            store_[i] = T();
            return i;
        }
        store_.push_back(T());
        return static_cast<int>(store_.size()) - 1;
    }
    T&       at(int i)    { return store_[i]; }
    void     release(int i) { free_.push_back(i); }      // 只标记回收位，元素原地保留
    int      size() const { return static_cast<int>(store_.size() - free_.size()); }
private:
    std::vector<T> store_;
    std::vector<int> free_;
};

// ============ 场景：2000 粒子的模拟帧循环 ============
struct Particle { float x, y, vx, vy, life; };
struct Bullet { int owner; float x, y; };

struct FrameWorld {
    static constexpr int kParticles = 2000;
    Particle particles[kParticles];

    FrameWorld() {
#if STEP >= 1
        alive.reserve(kParticles);       // 改造①配套：一次预留，此后 push_back 不再分配
#endif
#if STEP >= 2
        bullets.reserve(64);             // 改造②配套：池一次备足，acquire 不再触发搬家
#endif
    }

#if STEP >= 1
    std::vector<int> alive;                          // 改造①：升格为成员
#endif
#if STEP >= 2
    Pool<Bullet> bullets;                            // 改造②：池化
#endif

    void step(int frame) {
#if STEP >= 1
        alive.clear();                               // clear() 不缩容：容量续用
        std::vector<int>& alive_list = alive;
#else
        std::vector<int> alive_list;                 // 三宗罪①：帧内临时 vector，无 reserve
#endif
        for (int i = 0; i < kParticles; ++i) {
            Particle& p = particles[i];
            p.vy -= 0.1f; p.x += p.vx; p.y += p.vy; p.life -= 0.016f;
            if (p.life > 0.0f)
                alive_list.push_back(i);             // （Step0 路径）逐次扩容 → 反复搬家
        }

        int fired[8];                                // 存下标（swap-and-pop 语义下句柄会换位）
        for (int k = 0; k < 8; ++k) {
#if STEP >= 2
            fired[k] = bullets.acquire();            // 改造②：稳态下复用回收位，零分配
            bullets.at(fired[k]).owner = k;
            bullets.at(fired[k]).x = static_cast<float>(k);
#else
            fired[k] = 0;                            // 占位：Step0/1 无池
            Bullet* b = new Bullet{k, 0.f, 0.f};     // 三宗罪②：每帧 8 次 new/delete
            (void)b;
#endif
        }
        for (int k = 0; k < 8; ++k) {
#if STEP >= 2
            bullets.release(fired[k]);               // 当帧全灭：按句柄标记回收位，零分配
#else
            // Step0/1 的 delete 已并入上方
#endif
        }

#if STEP >= 3
        if (frame % 100 == 0) {                      // 改造③：日志分级——常规帧零格式化
            char buf[64];                            // 栈缓冲 + snprintf：无堆
            std::snprintf(buf, sizeof(buf), "[log] frame %d alive=%d\n",
                          frame, static_cast<int>(alive_list.size()));
            std::fputs(buf, stdout);
        }
#else
        std::string log = "frame " + std::to_string(frame)     // 三宗罪③：逐帧拼串
                        + " alive=" + std::to_string(alive_list.size());
        if (frame % 100 == 0) std::fputs(log.c_str(), stdout);
#endif
    }
};

int main() {
    FrameWorld w;
    for (int i = 0; i < FrameWorld::kParticles; ++i)
        w.particles[i] = {0.f, 0.f, 0.3f, 0.5f, 1.0f + (i % 64) * 0.01f};

    constexpr int kFrames = 300;
    std::vector<double> ms;                          // 帧时间收集（构造期分配不计入帧窗口）
    ms.reserve(kFrames);
    for (int frame = 1; frame <= kFrames; ++frame) {
        alloc_probe::g_frame_base = alloc_probe::g_count;    // 帧首记基线
        auto t0 = std::chrono::steady_clock::now();
        w.step(frame);
        auto t1 = std::chrono::steady_clock::now();
        std::size_t delta = alloc_probe::g_count - alloc_probe::g_frame_base;
        ms.push_back(std::chrono::duration<double, std::milli>(t1 - t0).count());
        if (frame == 1 || frame == 2 || frame == 5 || frame == 50 ||
            frame == 100 || frame == 200 || frame == 300)
            std::printf("第 %3d 帧：分配 %zu 次\n", frame, delta);
    }
    std::vector<double> sorted = ms;
    std::sort(sorted.begin(), sorted.end());
    std::printf("帧时间 p50=%.3f ms  p99=%.3f ms\n",
                sorted[ms.size() / 2], sorted[(ms.size() * 99) / 100]);
    return 0;
}
```

先说 `STEP` 宏这个设计本身：**同一份代码、四个宏值、四次构建**——而不是「改一版测一版再改回来」。它保证四个阶段测的是**除改动外完全相同**的代码（可复现纪律的实验版），也让你随时能一键回到任意阶段做对照。写实验程序时养成这个习惯，等于给自己留了一台「时间机器」。

计数器实现要点（每一条都是踩过的坑）：重载全部**四个**形态（new / new[] / delete / delete[]，ch02 只数了两个，数组形态防漏）；计数器内部**绝不 printf、绝不抛异常**（printf 自己可能分配 → 无限递归，继承 ch02 的纪律）；帧首记基线、帧末只打印**差值**（绝对计数无意义）；C++17 的对齐重载一句话说明（本演示不触发，真实工程补齐防漏计）。

四个阶段，每阶段一次构建、一次真实运行（Release `/O2`），看分配数逐级塌陷：

**STEP=0（起点，三宗罪俱全）**：

```text
第   1 帧：分配 29 次
第   2 帧：分配 29 次
第   5 帧：分配 29 次
第  50 帧：分配 29 次
frame 100 alive=93第 100 帧：分配 21 次
frame 200 alive=0第 200 帧：分配 9 次
frame 300 alive=0第 300 帧：分配 9 次
帧时间 p50=0.002 ms  p99=0.008 ms
```

29 次的分解（与 6.7/6.8/6.9 一一对号）：

- **约 20 次**：alive 向量从 0 长到 2000 的逐次扩容（MSVC 1.5 倍增，分配次数比想象的多）；
- **8 次**：Bullet new（三宗罪②）；
- **1 次**：字符串拼接冲出 SSO 边界后的堆分配（三宗罪③）。

粒子陆续死亡后 alive 变小，扩容次数随之下降——但每帧依然在分配。

**STEP=1（容器成员化 + reserve + clear）**：

```text
第   1 帧：分配 9 次
……
frame 300 alive=0第 300 帧：分配 9 次
帧时间 p50=0.002 ms  p99=0.007 ms
```

三宗罪①整笔消失（−20 次）：vector 升格为成员，`reserve` 一次吃满，之后每帧 `clear()` 复用容量。剩 9 = 8 次 new + 1 次字符串。

**STEP=2（Bullet 池化）**：

```text
第   1 帧：分配 7 次
第   2 帧：分配 1 次
第   5 帧：分配 1 次
第  50 帧：分配 1 次
frame 100 alive=93第 100 帧：分配 1 次
frame 200 alive=0第 200 帧：分配 1 次
frame 300 alive=0第 300 帧：分配 1 次
帧时间 p50=0.002 ms  p99=0.003 ms
```

三宗罪②整笔消失（−8 次）：`reserve(64)` 让池的 8 次 push_back 全部落进预留容量，之后 acquire 永远命中回收位，稳态每帧只剩字符串那 1 次。
（第 1 帧多出的几笔是 CRT/标准库首用的一次性初始化分配——locale、stdio 缓冲之流，第 2 帧起永久消失。这也是为什么看稳态帧、不看第 1 帧。）

**STEP=3（string_view / 日志分级 / snprintf 进栈缓冲）**：

```text
第   1 帧：分配 6 次
第   2 帧：分配 0 次
第   5 帧：分配 0 次
第  50 帧：分配 0 次
[log] frame 100 alive=93
第 100 帧：分配 0 次
[log] frame 200 alive=0
第 200 帧：分配 0 次
[log] frame 300 alive=0
第 300 帧：分配 0 次
帧时间 p50=0.001 ms  p99=0.003 ms
```

先把四步证据链收成一张表（数字取自上面的真实输出）：

| 阶段 | 改动 | 稳态每帧分配 | 消灭的是 |
| --- | --- | --- | --- |
| STEP=0 | 起点（三宗罪俱全） | 29 次（后期 9 次） | —— |
| STEP=1 | 容器成员化 + reserve + clear | 9 次 | 三宗罪①：约 20 次扩容 |
| STEP=2 | Bullet 池化 | 1 次 | 三宗罪②：8 次 new/delete |
| STEP=3 | string_view / 分级 / snprintf | **0 次** | 三宗罪③：1 次拼串 |

**「第 k 帧：分配 0 次」——这就是「主循环零分配有运行时证据」的检验标准③本体。
** 顺带如实交代：本例粒子规模小，帧时间 p99 只从 0.008ms 降到 0.003ms——零分配在这么小的负载下买到的不是毫秒，而是**预算的确定性**：300 帧里没有任何一次意外的分配尖刺，规模放大一百倍、堆开始碎片化之后，这笔账会以毫秒计。

收尾讨论两问：

- **为什么仪器要留在开发期，而不是跑一次就拆**？把计数器变成**分配预算断言**：Debug 下每帧 `assert(delta == 0)`——任何人不小心在帧循环里加了一行 `std::to_string`，当帧就崩给你看。这就是引擎团队的 alloc budget 纪律。
- **Release 下挂全局 hook 注意什么**？CRT/标准库内部的分配也会被计入（printf 的缓冲、locale 初始化……），所以用**帧间差值**消化噪声而不是看绝对数；发布版用宏开关把整个仪器摘除，只留 Debug 体检。

把这次的改造收成**任意零分配改造的通用五步**（值得背下来）：① 挂计数器拿基线证据；② 按类目分解分配（扩容类/生灭类/字符串类/其他）；③ 按 6.8 顺序逐类治理，每步复测；④ 用「稳态帧为 0」作验收线，而不是「变少了」；⑤ 断言常驻，防复发。

这台自制仪器离工业级方案只差工程化包装：真实引擎普遍内置 allocator 统计与「按帧/按标签」的分配报告（UE 的内存分析器一族就是重型版），原理与你刚写的完全同构——全局 hook + 分帧差值 + 预算断言。学会这台土仪器，那些工具的上手成本只剩界面。

## 常见误区

1. **在 Debug 配置下测性能下结论**（对位 Stages 原文）。
   - 症状：一测循环要几百毫秒，惊呼「C++ 太慢」或「我的渲染器不行」；
   - 病根：/Od 关优化叠迭代器调试层，测到的是调试脚手架的成本；
   - 纠偏：基准一律 Release /O2；顺手防编译器把被测代码优化掉（6.3 陷阱二）。
2. **热路径逐帧 new 与临时字符串拼接**（对位 Stages 原文「应成纪律而非优化项」）。
   - 症状：加特效或开日志就掉帧，剖析器看到 malloc/free 热点；
   - 病根：把分配当免费——次数税 × 60 帧，无声超支；
   - 纠偏：6.8 工具箱按序治理 + 分配计数器常驻（深入专题）。
3. **不测量就优化**。
   - 症状：凭直觉把怀疑的循环改了一遍，帧时间纹丝不动，有时反而更糟；
   - 病根：没有基线，「感觉慢」不可归因——优化的是想象中的热点；
   - 纠偏：先建基线，再走「问题-假设-改动-数据」四栏循环，数据说话。
4. **把 SoA 当教条**。
   - 症状：全部结构体强行拆字段，代码难看、帧时间不变；
   - 病根：忽略数据集规模与消费模式——L3 内 1.07 倍 vs L3 外 2.16 倍（本章实测），小数据集拆了白拆；
   - 纠偏：布局跟着「热点问哪些字段」走，先测量再拆（6.5 决策表）。
5. **微操语句与盲目内联**。
   - 症状：把 `i*2` 改成 `i<<1`、给小函数狂加 inline，收益为零；
   - 病根：热点在数据结构与分配上，不在单条语句；优化器比你强（Godbolt 看一眼就知道）；
   - 纠偏：火焰图找平顶，把精力花在 6.4–6.9 的「结构级」手段上。
6. **用 sleep/空转模拟负载做画像**。
   - 症状：剖析器显示「优化成功」，进游戏该卡还卡；
   - 病根：sleep 没有内存访问、没有分支、没有分配——负载形状与真实完全不同，测的是假问题；
   - 纠偏：负载用真实计算（参考本章各实验的浮点/遍历模拟），或直接对真实场景采样。
7. **用平均帧时间评估手感**。
   - 症状：报告写「平均 10ms，达标」，玩家仍然说卡；
   - 病根：尾部抖动被平均稀释——6 次 30ms 尖峰只抬高平均 0.4ms（6.2 实测）；
   - 纠偏：看 p99/直方图，把「偶尔卡一下」当成一级问题追查。
8. **把微基准冠军当游戏内结论**。
   - 症状：微基准快 3 倍的写法，游戏里毫无变化甚至更糟；
   - 病根：真空环境没有缓存竞争、分支污染、真实数据形状（6.3 陷阱四）；
   - 纠偏：微基准只下相对结论；绝对结论必须回游戏内剖析复测。

### 自测题

**1.** 三档预算：60fps = 16.67ms、144fps = 6.94ms、240fps ≈ 4.17ms；90fps 用 1000 ÷ 90 ≈ 11.1ms——口算方法是「1000 除以帧率」，别背表（§6.1）。
堆分配贵在哪，至少两条：① **分配器找块 + 多线程锁**：分配器要在空闲块结构里找合适的块，且 Windows 默认堆多线程安全，所有线程在同一把分配器锁上排队（§6.7 编号步骤 1–2；本章实验实测 55 倍差距）；
- ② **可能的系统调用**：空闲块不足时向 OS 要新页，一次成千上万周期，还可能伴随缺页（§6.7 步骤 3）；
- ③ **碎片化**：长跑进程空闲内存被切碎，RSS 涨、找块变慢、缓存局部性变差（§6.7 第二笔税）；
- ④ **缓存视角**：堆数据散落，指针跳转 = 潜在未命中（§6.4）。「次数比字节数敏感」的论证：字节数决定「占多少」，次数决定「交多少次税」——一次分配 1MB 和 1 字节走同一条分配器路径，而帧循环 100 次小分配就是 100 次完整征税；6.8 全部工具瞄准的都是「把次数降到 0」（§6.7 末段）。

**2.** ① 前三大耗时点：`Particle::integrate`（31%，宽平顶 = 自耗时大头，第一目标）、`Physics::step`（15%，整块皆平顶——没有更深的子块分担，说明是它自己的循环在烧）、`Mesh::bind`（14%，平顶）。
判断依据：**平顶**（宽而浅的矩形）才是自耗时大头——`ParticleSystem::update` 虽有 38% 横宽，但纵深之下有 integrate 扛着 31%，它自己只是调度者；`GameWorld::update` 的 52% 同理是「含子调用的占比」，不能直接定罪（§6.2）。

② 下一步两路：先用**帧计数器**确认这三个点在 p99 尖峰帧里是否也在场——排除「平均热点、偶发无关」的干扰；再按嫌疑类型下钻：integrate → 查数据布局（AoS？冷字段同住？→ §6.5）与贵运算（归一化的 sqrt+除法？→ §6.10）；bind → 查提交路径的分配与状态切换（→ §6.7/6.8）；怀疑跨线程干扰 → **时间线**看主线程块的等待缺口（§6.2③）。

**3.** ① 机制：热循环只消费 28B 热字段（pos/vel/life），AoS 每粒子却是 44B——color 的 16B 冷字段与热字段**同住缓存行**。
缓存行的交付粒度是 64B 整条（§6.4 步长实验），于是每次为热字段买单，都有一截带宽花在永远不读的 color 上；100 万粒子约 41MB 冲出 L3 后，每次未命中都要去 DRAM 搬整条行，浪费全部显形——2.2 倍由此而来（§6.5 实测 2.16 倍同机制）。

② 缩到 10 万（约 4MB）时整个数据集**常驻 L3**：首次未命中之后，数据（连同冷字段）全在 L3 里被反复复用，为冷字段多搬的行停在 L3 里，不再交 DRAM 的税——大缓存把布局错误兜住了（1.1 倍）。

③ 由此得出 AoS 不差的两个条件：**数据集小到常驻 L3**（浪费被缓存兜住），或**字段总是整组消费**（没有冷字段，同住不浪费）——布局跟着「热点问哪些字段」走，先测量再拆（§6.5 决策表）。

**4.** 至少五处，任答三处合格：① **Debug 配置**——/Od 叠迭代器调试层，量出来的是脚手架成本，必须 /O2（陷阱一）；
- ② **结果未被消费**——`for(int x:v) x+1;` 无任何副作用，优化器有权把整个循环消除，计时≈0；必须 volatile sink 或打印消费（陷阱二）；
- ③ **单轮 + 无预热**——冷缓存与预测冷启动的「开机税」进了样本，应预热后多轮取稳态（陷阱三）；
- ④ **计时窗口含构造**——`vector` 构造（含 1 亿次初始化写入）被算进基准，测的是构造+遍历的合账——构造移到计时外；
- ⑤ **结论形式**——只报一个绝对毫秒数：微基准只下相对结论，应报倍数并注明机器与口径（陷阱四）。顺带：本例 vector 大小固定、无需 reserve，但工程里构造即 reserve 是习惯（§6.3）。

**5.** ① **new 去哪了**：池构造/首用时一次性 `reserve` 把内存全拿到手，此后 acquire 复用回收位（free 栈弹出）或落进预留容量——稳态下堆操作次数为 0，「new」变成了「从池里拿一个已付过费的位」（§6.8）。

② **碎片消失**：池内对象同尺寸、住在一块连续内存里——不存在「反复分配释放不同大小把空间切碎」的原料；对堆也友好：池只向堆要少数几个大块，分配 pattern 简单（§6.7 第二笔税的对症药）。

③ **swap-and-pop 的 O(1)**：删除 = 尾部元素与空洞位换位 + pop——只动两个元素，与容器长度无关；代价两条：**不保序**（遍历顺序变化），**其他元素的下标/引用换位失效**。
下标失效场景：锁定系统存了 17 号弹幕的下标，同帧 3 号消失触发换位，若 17 号恰是被搬的尾弹，下标 17 现在指着无关对象——正解是回收位标记版池（下标终身有效）或世代号校验（§6.8 警示场景）。

**6.** ① 平均的数学骗局：300 帧里 6 帧 30ms——p99 已被顶到 30ms，平均却只从 9.83 涨到 10.25ms（§6.2 实测）。
玩家对**每一次卡顿**都有感知，对「平均」毫无感知；手感对应的是尾部分布，不是均值——这就是为什么 6.1 说「帧时间一致性 > 平均值」。

② 三个候选来源与确认仪器：**偶发堆分配**（某处新加的 new 触发尖峰）→ 分配计数器按帧分段，哪帧暴涨一查便知（深入专题）；**异步线程交互**（加载收尾 join、锁等待占用主线程）→ 时间线看主线程块的等待缺口（§6.2③）；**OS/驱动/vsync 干扰**（后台进程抢占、vsync 档位跳变）→ 帧计数器的分布形态辅助判断——vsync 跳档的帧时间会精确落在 33ms 附近，而抢占的尖峰位置随机（§6.1）。

**7.** ① 每帧重建的 `vector<int>` → **成员化 + reserve + clear**：第一档手法，改三行，稳态零分配（§6.8）；
- ② 高频生灭 → **对象池**：粒子/子弹的原型主场；按系统是否靠下标互指选回收位版（下标终身有效）或 swap-and-pop 版（遍历更紧凑）（§6.8）；
- ③ 用完即扔的大宗临时数据 → **arena/帧分配器**：当帧生当帧死，帧末 bump 指针一拨全清（§6.8）；
- ④ 帧内拼 key → **string_view 借用 + 高频 key 静态化/缓存**：分配计数器头号惯犯，能借就不拼、能缓存就拼一次（§6.9）；
- ⑤ 逐粒子 `v / sqrt(len)` → **先火焰图定罪**：罪成则向量化 + rsqrt 近似（§6.10），或按 6.6 思路把归一化挪出热循环——这是全清单里最需要「先测量」的一项，因为它在微基准里总是「有效」。

**8.** 从「风险的时间分布」论证：分配纪律的破坏者是**未来的每一次代码提交**——任何人在帧循环里加一行 `std::to_string`、加一条日志，分配就无声回归。
一次性测试只能证明「历史版本干净」，挡不住未来；而且分配回归的症状（偶发卡顿）**延迟显形、难以定位**——等「有时候卡一下」的 bug 单飘进来时，污染点早已埋进几十次提交里。
常驻的 alloc budget 断言把反馈延迟压到**当帧**：Debug 下每帧分配一非零就崩，肇事提交当场暴露。
成本核算：计数器只在 Debug 构建存活（Release 用宏开关整体摘除），运行时开销是每帧一次差值比较——用一次比较，买「纪律不可无声腐化」这个不变式，是全章性价比最高的一笔交易（深入专题收尾两问）。

## 构建与运行速查（Windows + VS2022）

全章纪律，十条带走：

1. 一切计时 Release `/O2`，Debug 数据只看正确性；
2. 帧时间看 p99/直方图，不看平均；
3. 「哪里慢」问剖析器，「抖不抖」问帧计数器，「谁等谁」问时间线；
4. 微基准：预热、多轮、固定负载、结果必须被消费、只下相对结论；
5. 数据布局跟着「热点问哪些字段」走——数据集出 L3 才谈 SoA 收益；
6. 分支三条件（热循环/数据决定/两侧有量）全中才优化；
7. 帧循环盯「分配次数」不是「分配字节数」——零分配是纪律不是优化项；
8. 工具顺序：reserve/成员化 → 池 → arena；能上栈先上栈；
9. 热路径字符串：要么借用，要么不存在；
10. 贵运算清单是嫌疑人名单——火焰图定罪，再动手。

```bat
:: 正确性验证（W4 零告警基线）
cl /nologo /utf-8 /std:c++20 /EHsc /W4 源文件.cpp
:: 一切性能计时（全章纪律：必须 /O2）
cl /nologo /utf-8 /std:c++20 /EHsc /W4 /O2 源文件.cpp
:: 零分配解剖的四阶段
cl /nologo /utf-8 /std:c++20 /EHsc /W4 /O2 /DSTEP=0 zero_alloc.cpp & zero_step0 …
```

> 提醒：`/DSTEP` 四个阶段请分别生成四个可执行文件再各自运行（宏在编译期定型）；直接改一个 exe 反复重编也行，但保留四份产物方便对照——本章深入专题的全部输出块就是这么产生的。
